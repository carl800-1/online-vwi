# ESOP 发布系统 · 技术方案

> 版本 **v0.4.2**　日期 2026-10-21　状态：M0–M4 已按此实现（v1.3.0）
> 依据：`docs/02-需求确认书.md` **v0.5.0**（切换时限放宽到 5 分钟；本地只留 1 套）。
> 本文只回答"怎么做"，不新增需求。凡与确认书冲突处，以确认书为准。
>
> **v0.4.1 修订**（PATCH：实现层面修正，协议与需求均不变）：
> ① 5.1 / 5.2 的"目录三步 rename"改为**文件级共存 + 精确删除**——跨进程 rename 必然产生可测黑屏，违反 A2；
> ② 补充 exe 的进程结构（主进程独占网络与磁盘、渲染层只显示）、配置优先级、维护逃生快捷键；
> ③ `/display/playlist` 响应补 `ext` 字段（终端按扩展名存盘，缺了会让 `<video>` 解不出来）。
>
> **v0.4.0 修订**（MINOR：时限放宽带来的简化，切换协议由单段改为**两段式**）：
> ① 取消预取与双槽——删 `prefetch_model_id`，`setting` 改为 4 把钥匙（current / seq / pending_model / pending_deadline）；
> ② `/api/switch` 改为**两段式**：`prepare`（喊大家下载）→ 终端 `POST /api/ready` 举手 → 服务端集齐后 `activate`；
> ③ 新增接口 `POST /api/ready`，接口数 **12 → 13**；
> ④ 终端本地只留 **1 套**（27MB），切换时现场下载，删旧目录；
> ⑤ 新增 5 分钟超时强翻 + 掉队告警路径（A10）。
>
> **v0.3.0 修订**（MINOR：承载确认书 v0.4.0 的两条切换纪律，结构不变）：
> ① 切换语义定为**原子切换**——`seq` 一次跳变唤醒全部终端，**先备齐后翻**，无"边下边播"路径；
> ② 终端缓存由"全量预下发 10 型号"改为**双槽 A/B**（当前 + 预备），本地常驻 2 套 ≈ 54MB，
> 切换成功后**立即删除旧槽**，不做历史归档；
> ③ `setting` 增加 `prefetch_model_id`；`/api/state` 响应增加 `prefetch` 字段；
> ④ 新增"内容不全"降级路径（允许切、必须顶栏告警）。
>
> **v0.2.0 修订**（破坏性变更：取消工位实体）：数据表 6 → **5 张**（删 `station`，新增 `setting`）；
> 接口重排为 **12 个**（删 3 个工位接口，加 `/api/processes`）；终端不再有令牌，身份 = 工序代码 `op`；
> 换型由"逐台改型号"改为"改一个全局值 + 唤醒长轮询"。

## 0. 一页结论

| 项 | 决定 |
|---|---|
| 服务器 | 一台 Windows 电脑，Node 22 + **内置 SQLite**，零 npm 依赖 |
| 接收端 | Electron exe，1280×1024 设计稿 + 缩放，kiosk 全屏 + 开机自启 + 看门狗 |
| 层级 | **机种 → 工序 → 清单**，到此为止，无工位（v4.0.0 又把工位层删掉了） |
| 终端身份 | 启动参数 `?op=OP30`，只此一个值，不注册不建档案 |
| 切换通道 | **长轮询**（挂 25 秒）+ 30 秒兜底，不用 WebSocket/SSE |
| 内容存储 | `media/<sha256前16>.<ext>` 内容寻址，天然去重 |
| 切换语义 | **两段式原子切换**：`prepare` → 全员 `ready` → `activate`，5 台同帧翻 |
| 终端缓存 | **单套**：只有当前型号 × 本工序 ≈ **27MB**，切完即删 |
| 切换耗时 | 正常 **3–6 秒**；验收上限 **5 分钟**；掉队超时强翻 + 告警 |
| 数据表 | **9 张** |
| 接口 | **38 个**（含 3 个向后兼容的旧地址） |

一句话：**服务器存内容、记一个"现在做哪个型号"；换型时先喊大家去下载，5 台都下完了再一起喊翻，翻完各自删掉旧文件。终端盘上永远只有一套内容。**

## 2. 数据模型（9 张表，v4.0.0 起内容挂「机种 × 工序」）

```sql
-- 线体：一条物理产线。
--   status  = 给人看的四态：running / stopped / maintain / care（运行中 / 停线 / 维修 / 保养）
--   enabled = 给机器看的开关，由 status 派生（只有 running 才为 1）
--   slots   = 这条线实际有几块屏，**只做展示**，不卡校验
--   v3.5.0 起允许多条线同时 running（现场每条线有自己的终端，各带 ?line=）
line       (id, code UNIQUE, name, enabled, status, slots, sort, created_at)

-- 机种（原"产品型号"）：全厂共用
model      (id, code UNIQUE, name, enabled, sort)

-- 可生产机种（v4.0.0）：机种勾了哪几条线。以前靠 station 的 DISTINCT 隐式表达，
-- 工序归机种之后这个关系必须单独存，否则"这个机种能在哪几条线做"没人知道。
model_line (model_id, line_id, sort, PRIMARY KEY(model_id, line_id))

-- 工序：挂机种，是终端身份的一半（另一半是线体）。code 只在本机种内唯一。
-- 它同时是内容的宿主：允许类型、体积上限、播放方式、内容清单都挂在它下面。
process    (id, model_id, code, name, sort, max_mb, note, play_mode,
            import_batch, UNIQUE(model_id, code))

-- 工序要求：有行 = 允许这类文件，min_count = 至少几份
process_req(process_id, kind 'image'|'video'|'pdf', min_count,
            min_width, min_height, UNIQUE(process_id, kind))

-- 媒体：内容寻址，同一文件只存一份
media      (id PK = sha256 前 16 位, sha256, kind, ext, bytes,
            width, height, duration_ms, src_sha, page_no, created_at)

-- 播放清单项：(机种 × 工序) 下的一条
item       (id, model_id, process_id, ord, kind, media_id,
            dwell_sec, fit, zoom, UNIQUE(model_id, process_id, media_id))

-- 全局状态：KV
setting    (key PK, value)     -- rev（通信序号，全局单调）

-- 每条线体自己的换型状态
--   pending_* = 正在切（切完就清）；next_model_id = 排产，排好了还没开始切
line_state (line_id PK, current_model_id, pending_model_id, pending_deadline,
            next_model_id, seq)
```

**v4.0.0 的核心变化：删掉「工位」这一层，工序自己就是内容宿主。**

v3.0.0 用「机种 × 线体 × 工位」是为了解决"两条线工序码含义不同"。但用了一年发现代价太大：
两道工序的机种放到两条线上要维护 4 个工位，全是空壳；改一道工序要改所有线的同码工位，
漏一条就一边新一边旧。而实际上**工艺跟着产品走** —— 同一机种在哪条线做，装配还是装配。

现在两层，谁都不越界：

| 层 | 管什么 | 表 |
|---|---|---|
| 机种 | **产品本身 + 它有几道工序、每道看什么** | `model` + `model_line` + `process` + `process_req` + `item` |
| 线体 | 这条线的**身份、状态、几块屏** | `line` + `line_state` |

取内容时：

```js
processOf(currentModelId, op)   // 机种 + 工序码，两步定位，不再需要"先找线"
```

**为什么这次敢删**：工位存在的唯一理由是"跨线内容要不一样"。现场确认过：同一个机种在几条线
上做的是同一套工艺，真有个别差异就加一道专属工序。而"机种 × 线体"这个关系本身仍然需要
（要能回答"这个机种在哪几条线做"），所以拆出一张纯关联表 `model_line` —— 它没有内容、没有排序，
只有"C 位"这一件事，增删一致性天然成立（主键即约束）。

**`station` / `station_req` 两张表在 4.0.0 之后是空的**：建表语句还留在 `SCHEMA` 里，是为了让
老库的搬家路径只有一条（1.x → 2.x → 3.x → 4.0 一路走通），业务代码不再读写，迁移那一步会清空。

**为什么换型状态必须按线体拆**：一线在跑 X200 时二线可能在跑 X300。
如果还放在全局 `setting` 里，一条线换型会把另一条线的当前机种也改掉 —— 那正是多产线现场最容易出的错。
`line_state` 每行一条线，`seq` 也各算各的。`rev` 仍然全局单调，长轮询用它判断"有没有新信息"。

**举手名单（ready）不落库**，放内存 `Map<"lineId|op", {modelId, readyAt}>`：重启后清空，
各终端下一次 `POST /api/ready` 会重新补上。丢一次举手名单的代价只是"多等几秒"，
而落库反而要处理过期清理，不划算。在线表同理，记账键也是 `lineId|op`。

**终端身份 = 线体 + 工序**。`?line=L1&op=OP30`。不带 `line` 时回落到"当前启用的线体"，
这是给现场老终端留的后路（它们的 `config.json` 里没有 `line` 字段）：升级服务端后继续能跑。
`op` 在本机种里不存在时**不回 404**，而是 200 + `noStation` + 提示 —— 404 在终端上表现为
"连不上服务器"，现场会去查网络，排查方向全错。

**刻意不建的表**：`user` / `session`（不做权限）、`release`（不做版本治理）、`play_log`（不做统计报表）、`page` / `block`（不做版式）、`switch_log`（切换记录写进程日志即可）。
屏没有"设备档案"：只配 `line` + `op`，不注册、不逐台设置。

### 2.1 老库迁移（自动、幂等，三次搬家一次收口）

`openDb()` → `migrate()`，按"现在长什么样"决定从哪一步接上，全部幂等（先 `PRAGMA table_info` 再改）。

**4.0.0 的入口短路**：`migrate()` 第一句就是

```js
if (colsOf('process').has('model_id')) return;   // 已经是 4.0.0，只补增量列，到此为止
```

少了这句，`migrate()` 会按 `line_id` 把 `process` 重建回去 —— 一开库就把新结构砸了。

**不可逆，所以先备份**：`openDb()` 里 `backupBeforeV4()` 先探"有 `station` 表**且** `process` 没有
`model_id`"，满足才把 `vwi.db` 复制成 `vwi.db.pre4.bak`，只备一次；备份失败不阻断启动，只写日志。

| 从哪来 | 走哪段 | 做什么 |
|---|---|---|
| 1.x（`item.process_id`） | `migrateToStations()` | 关外键 → 建新 `item` → 按「机种 + 工序码 + 工序所属线体」搬 → drop → rename |
| 2.0.0（`station` 没线体列） | `migrateStationsToLines()` | 老工位复制到所有含同名工序码的线体（宁多不漏），日志 `N → M` |
| 3.x（`station` 还在，`process` 有 `line_id`） | `migrateToModelProcess()` | 建 `process_v4` / `process_req_v4` / `item_v4` → 工位并成工序 → 建 `model_line` → 回填 `slots` → drop 老表 → rename |

`migrateToModelProcess()` 的合并规则（同名工序码跨线并成一条）：

- 名称 / 排序 / 体积上限 / 说明取**排序最前的线**那一份
- 允许类型按 kind 取并集（`min_count`、最小分辨率取最大，宁严不松）
- 内容按 `ord` 顺序拼接，同一 `media_id` 只留一条（去重计数打日志）
- `line.slots` 按这条线实际有过的工序码个数回填；`station` 表为空时不动（保持默认 5）

日志：`[db] 已升级到 4.0.0：工位并入工序（合并 N 个跨线工位，去重 M 条内容）`。
两个数都不为 0 说明**两条线原来的内容确实不一样**，合并只留了一份 —— 现场要人工过一眼。

> **回滚要 exe + 库一起换**。老 exe 读新库不报错，只是「什么都没配」，很难当场反应过来。

> **索引不能写进 SCHEMA**：老 `item` 表没有 `process_id` 列，`CREATE INDEX` 会在 `openDb()` 直接抛
> `no such column`，库都打不开。所有索引统一放在 `migrate()` 末尾建（那时结构一定已就位）。

> `ensureStation()` / `ensureStationsForLine()` / `copyStations()` / `saveStation()` 这些 3.x 的
> 辅助函数在 4.0.0 已随工位层一起删除；建工序改走 `createDefaultProcesses()`（新建机种时）与
> `saveProcess()`（界面上增删改）。

## 3. 接口

| # | 方法 | 路径 | 说明 |
|---|---|---|---|
| 1 | GET | `/api/board` | **总览**：全部线体（带 `status` 与 `nextModelCode`）+ 每线客户端状态 + `hasContent`，外加 `overview` 四态统计，一次拿完 |
| 2 | POST | `/api/board/switch` | 总览页换型，回 `{ok, activated, phase}`（无终端在线时直接激活） |
| 2a | POST | `/api/board/next` | **排产下一个机种**：`{lineId, modelCode}`，只写 `line_state.next_model_id`，**不动终端**；`modelCode` 传空 = 取消排产 |
| 3 | GET | `/api/models` | 机种列表：`done/total`（已配工序数 / 工序数）、`lines`（可生产线体，含各线状态） |
| 4 | POST | `/api/models` | **新建机种**：`{code, name, processCount, lineIds[]}` —— 一次把 `OP1…OPn` 铺好并挂上可生产线体 |
| 4a | PUT | `/api/models/:id` | 改机种（编码 / 名称 / 停用 / `lineIds[]` 整批覆盖可生产线体） |
| 5 | GET | `/api/processes?modelId=` | 某机种的全部工序（含 reqs、`playMode`、items） |
| 6 | POST | `/api/processes` | 加一道工序（`{modelId, code, name?}`） |
| 7 | PUT | `/api/processes/:id` | **保存**：`name/note/maxMb/playMode/reqs/items` 只传哪块改哪块，其余不动（五个字段各判 `!== undefined`） |
| 8 | DELETE | `/api/processes/:id` | 删工序（连它的 `process_req` 与 `item` 一起，CASCADE） |
| 10a | POST | `/api/import/parse?filename=` | **解析工序表**（`.xlsx` / `.csv`），body 是文件本身；**认表头名不认列号**，逐行判 `new / same / diff / bad` 并给原因，**不落库**。没有机种列的老表用 `?modelId=` 兜底 |
| 10b | POST | `/api/processes/import` | **按确认过的行批量建/更新工序**：`{rows:[{row,modelId,code,name,note}], mode: merge\|update\|update-only}`；返回 `created/updated/kept/skipped/bad/batchId` |
| 10c | POST | `/api/processes/import/undo` | **撤销某批次新建的工序**：`{batchId}`，只删本批新建（`process.import_batch` 对位），改名不回滚 |
| 10d | GET | `/api/export/processes.xlsx` | **导出工序清单（全厂一张表）**：四列 `机种 / 工序码 / 名称 / 做什么`，与导入模板逐列同构，改完能整份导回；`?modelId=` 可只导一个机种 |
| 10e | GET | `/api/export/template.xlsx` | **导入模板**：标题行 + 两行示例，第二页是填写说明（不放在数据区，否则会被当成一道工序） |
| 11 | GET / POST / PUT / DELETE | `/api/lines[/:id]` | 线体增删改：`{name, slots, status}`，编码自动生成 `L1/L2…`；**删线只断"可生产"关系，机种与内容不动** |
| 14 | GET | `/api/playlist?modelId=&processId=` | **兼容接口**：`processId` / 老调用方的 `stationId` 都认 |
| 15 | PUT | `/api/playlist` | 兼容接口：整批保存 |
| 16 | GET | `/api/playlist/all?modelId=` | 一次取某机种全套清单 |
| 17 | POST | `/api/media/upload?filename=&kind=` | 流式上传，返回 sha 与宽高 |
| 18 | GET | `/api/media` | 媒体库（带被引用次数） |
| 19 | POST | `/api/media/gc` | 清理无引用媒体 |
| 20 | POST | `/api/switch` | **核心**：`{modelCode, lineId}` 发起切换（进 prepare，**不立即生效**） |
| 21 | POST | `/api/ready` | 终端举手 `{line, op, modelId}`：本工序内容已备齐并校验通过 |
| 22 | GET | `/api/state?line=&op=&since=` | **长轮询**：`{seq, phase, modelCode, deadline, online[], ready[]}` |
| 23 | GET | `/display/boot?line=&op=` | 终端启动自检：我是谁、现在该播什么 |
| 24 | GET | `/display/playlist?line=&op=&model=` | 拉**指定机种**本工序的清单与媒体地址 |
| 25 | GET | `/m/:id` | 媒体文件，支持 Range |
| 26 | POST | `/api/telemetry` | 终端上报机器参数与下载进度（只写内存，不 bump rev） |
| 27 | GET | `/api/terminals?lineId=` | 每道工序的终端实时参数 |

管理界面本身是静态文件，不占接口。

**为什么 `PUT /api/processes/:id` 敢做成"部分更新"**：媒体库只发 `{reqs, items}`、机种设置只发
`{name, note}`、播放方式只发 `{playMode}`，三处都能改同一个对象而不互相覆盖。
闸门只在 `saveProcess()` 一处：五个字段各判 `!== undefined`，未传的键**保持原值**，
`items` 传了就在事务内先删后插。改这块之前先确认这个前提没破。

**已退役**（4.0.0）：`/api/stations*` 七个接口（含 `sync` / `copy`）整组下线 —— 工位层没了，
"跨线复制"也不需要了，因为两条线本来就共用同一套内容。
更早退役的还有 `/api/profiles*` 四个接口（配置库，v2.0.0）。

**终端不鉴权**：只带 `op` 参数，没有令牌。因为一期没有权限体系、只部署在内网，工序代码也不是秘密。
代价是内网任何人能拉到内容——可接受，但**服务器绝不能直接暴露到办公网或外网**。

## 4. 切换协议（决定 A1 / A9 能不能过）

### 4.1 两段式：prepare → ready → activate

服务端只有一个三相状态机，没有别的：

| phase | 含义 | 进入方式 |
|---|---|---|
| `idle` | 稳定在某型号，大家正常播 | 初始 / activate 之后 |
| `prepare` | 正在让全线下载新型号，**尚未生效** | `POST /api/switch` |
| （内部）| 收齐举手，或到 5 分钟 | 服务端自己判断，然后 activate |

**第一段 `POST /api/switch {modelCode}`**——注意这里**不动 `current_model_id`**，所以工人看不出任何变化：

```sql
BEGIN;
  UPDATE setting SET value = :targetModelId       WHERE key = 'pending_model_id';
  UPDATE setting SET value = :now + 300000        WHERE key = 'pending_deadline';
COMMIT;
-- 唤醒所有挂起的长轮询 → phase='prepare'
```

**第二段**：终端下完各自 `POST /api/ready {op, seq}`。服务端每收到一个就检查一次：

```js
function maybeActivate() {
  if (phase !== 'prepare') return;
  const onlineOps = [...online].filter(o => Date.now() - o.lastSeen < 60_000).map(o => o.op);
  const allReady  = onlineOps.every(op => ready.get(op)?.modelId === pendingModelId);
  if (allReady || Date.now() >= pendingDeadline) activate();
}
```

`activate()` 才真正改状态：

```sql
BEGIN;
  UPDATE setting SET value = (SELECT value FROM setting WHERE key='pending_model_id')
   WHERE key = 'current_model_id';
  UPDATE setting SET value = CAST(value AS INTEGER) + 1 WHERE key = 'seq';
  DELETE FROM setting WHERE key IN ('pending_model_id','pending_deadline');
COMMIT;
-- 唤醒长轮询 → phase='idle' + 新 modelCode + 新 seq
```

**三个关键判断，都有代价在背后**：

| 决定 | 为什么 |
|---|---|
| **分母用"在线终端"而不是常数 5** | 某台屏今天没开机、或只装了 3 台，用 5 做分母就永远等不齐，每次都要拖到 5 分钟。分母取"最近 60 秒有过请求的 op" |
| **超时也强 activate，不无限等** | 一台网络烂就全线停产，这比"个别屏晚一点"严重得多。掉队的那台见 4.4 的告警 |
| **`seq` 只在 activate 时 +1** | prepare 期间 `seq` 不变，终端不会误判"要翻了"。这是"准备中"和"已切换"在协议层的分界 |

`GET /api/state?since=N`：
- `seq > N` → 立即返回 `{seq, phase, modelCode, deadline, online, ready}`
- 否则挂起，最多 25 秒；超时返回当前值（让终端确认链路活着，同时兼作心跳）
- **prepare 期间即使 `seq` 没变也要返回**（因为它带 `phase` 和 `deadline`），否则终端永远不知道要开始下载

`online` 来自内存 `Map<op, lastSeenAt>`，随每次 `/api/state` 与 `/display/playlist` 刷新，**不落库**；`ready` 同理。
服务重启后 30 秒内随终端心跳自动重建——代价只是重启那一次切换可能提前 activate，可接受。

**为什么"等齐了才喊"就是"一起切"**：5 台终端挂的是同一条长轮询，`activate()` 后遍历挂起表逐个 `resolve`，
在同一个事件循环 tick 里完成，彼此间隔**微秒级**。真正决定"齐不齐"的是前面的举手机制，不是这最后一下广播。

### 4.2 终端：一个循环，三个分支

终端只保存两个值：`appliedSeq`（已生效的 seq）和 `localModel`（本地盘上现在是哪个型号）。

```
loop:
  r = GET /api/state?since=appliedSeq          (25 秒超时)

  ── 分支① 准备中 ──────────────────────────────
  if r.phase == 'prepare' && r.pendingModel != localModel && 当前没在下载它:
      startDownload(r.pendingModel)             // 画面照旧播旧内容，顶栏挂"准备中 3/11"

  ── 分支② 该翻了 ──────────────────────────────
  if r.phase == 'idle' && r.seq > appliedSeq:
      if 本地已备好 r.modelCode:
          flip(r.modelCode)                     // 同步翻（见 4.4）
          appliedSeq = r.seq
      else:
          掉队：保持旧画面 + 顶栏红字告警，继续下载，下完再自己翻（见 4.4）

  ── 分支③ 其余 ────────────────────────────────
  什么都不做（超时心跳，顺便刷新 online）
```

**关键设计：状态机而不是命令队列。** `seq` 表达"现在应该是什么型号"，不是"请执行第 N 号命令"。
所以班长连点三次 X300 → X400 → X300：

- 终端①次收到 prepare X300，开始下
- 第二次收到 prepare X400 → **取消 X300 的下载**，改下 X400（`pendingModel` 变了）
- 第三次回到 X300 → 再取消再重下

只有中间态被跳过，最终必然收敛到 X300。**不会出现"翻到 X400 停 200ms 再翻回 X300"的闪动**，这是 A9 的保证机制。

> 取消重下会浪费已下的流量，但"连点三次切换"本身就是误操作，不是常态。
> 优化它（比如保留已下完的文件做增量）会把逻辑复杂度翻倍，不值得——27MB 重下只要几秒。

### 4.3 下载与校验：先落 tmp，校验通过才换指针

| 步骤 | 动作 |
|---|---|
| 1 | `GET /display/playlist?op=OP30&model=X400` → 清单（每个媒体的 id、sha、字节数、停留秒数） |
| 2 | 建临时目录 `tmp/<modelId>/`，逐个下载 |
| 3 | 每下一个就校验 sha256；不符 → 删掉重下一次；再不符 → 记"缺失"继续下一个 |
| 4 | 顶栏实时更新 `准备中 3/11`（每完成一个 +1） |
| 5 | 全部完成（含"缺失"降级）→ `POST /api/ready {op, modelId}` |
| 6 | 等 activate 推过来；若已被超时强 activate，自己下完后自愈翻页 |

**为什么下到 `tmp/` 而不是直接覆盖当前目录**：切换失败、中途断电、网络断了换回原型号——
任何一种情况下，**旧内容必须完好无损**。这是 A2（不黑屏不闪白）和 A4（断网 8 小时不断播）的底线。
tmp 下完且校验通过后，才在 flip 那一刻把目录指针换过去。

**为什么单文件串行，不并发**：5 台终端 × 每台多文件并发，会把 AP 队列打满，正在播的视频直接卡顿。
27MB 串行在 1Mbps 下也就 3.6 分钟，稳稳落在 5 分钟窗口内。**用并发度换"播放不受影响"，这笔交易值。**

**下载中断怎么办**：断电/断网后重启，`tmp/` 里可能留半截文件。启动时**整个 tmp 目录删掉重下**——
判断"哪个文件下完了"的成本比重新下 27MB 高，而 27MB 只要几秒。这是刻意选的笨办法。

### 4.4 翻页与删旧（A8 / A9 / A10 的落点）

翻页必须是一个**同步函数**，中间不含任何 `await` / `setTimeout`：

```js
function flip(newDir, items) {       // 同步执行
  player.stop();                     // ① 停 <video>，释放文件句柄
  player.setQueue(items);            // ② 换队列，回到第 1 项
  player.start();                    // ③ 首项立即渲染
  const old = currentDir;
  currentDir = newDir;               // ④ 单槽：直接换指针
  writeIndex({ dir: newDir, items });// ⑤ 落 index.json
  setImmediate(() => purge(old));    // ⑥ 渲染让出去之后再删旧目录
}
```

**① 为什么 `stop()` 必须在最前面**：Windows 上 `<video>` 占着文件时 `rm` 必然失败。
先停播释放句柄、再换指针、最后才删——**顺序错了 A8 永远过不了**，这是实机才会暴露的坑。

**⑥ 为什么 `purge` 要 `setImmediate`**：删 27MB 在主控盘上可能几十毫秒，同步删会卡住下一帧，A2 立刻破。
让它离开当前 tick，画面先翻过去，删除在后台完成。

`purge(old)` 的实现与兜底：

1. `fs.rm(old, { recursive: true, force: true })`
2. 成功 → 日志 `[switch] purged X300 27.1MB`
3. 失败（`EBUSY` / `EPERM`）→ 进 `pendingPurge` 队列：**60 秒后重试 → 启动时重扫 → 连续 3 次失败顶栏告警**
4. 无论成功失败，`index.json` 只保留当前目录（下次启动不会把旧目录当有效内容）

> 这条兜底不是可选项。**没有它，A8 在实机上大概率通不过**——视频文件被解码器占住是必然发生的，
> 而"删不掉就静默跳过"会让磁盘在几周后悄悄堆满旧型号。

**掉队者的自愈（A10 的另一半）**：超时强 activate 时没备完的那台，此刻状态是 `phase=idle, seq=43, modelCode=X400`，
但它盘上还是 X300。它继续下载，下完后**先 flip 再更新 `appliedSeq = 43`**，红字告警自动消失。

**红字要能挡住"开始作业"的冲动**：`内容未就绪 · 请勿作业`，红底白字 + 边框闪烁（CSS 动画实现，不用 JS 定时器）。
工人看到这个，不会误以为自己看的是新型号——这是 A10 存在的全部意义。

### 4.5 为什么用长轮询，不用 WebSocket / SSE

- 长轮询在原生 `http` 上就能写，零依赖；SSE 要处理分块与断流重连；WebSocket 要引 `ws`
- 25 秒挂起 ≈ 一次普通请求，无线抖动时重连成本极低
- 断线后终端 30 秒兜底轮询，网络恢复自动接上，**不需要任何重连状态机**
- 切换是**低频事件**（每天 2–3 次），长轮询的"多一次握手"完全无所谓；反向 WebSocket 常连接在无线车间反而是负担

### 4.6 带宽预算：5 分钟为什么一定够

| 场景 | 需要 | 现实 |
|---|---|---|
| 单台在 5 分钟内下完 27MB | **90KB/s** | 车间任何可用的 WiFi 都远超这个 |
| **5 台并发**（最坏同时切） | 5 × 90KB/s = **450KB/s ≈ 3.6Mbps** | 5GHz 40MHz 单 AP 实测 ≥20Mbps，**5 倍余量** |
| 正常情况（实际吞吐 200Mbps） | 135MB ÷ 25MB/s | **约 6 秒** |

所以双槽预取、错峰限速这些手段全部不需要——**带宽本来就不是瓶颈**，瓶颈原来是"要求 10 秒"这个人为约束。

**真要担心的不是慢，是断**：下载中途掉线会导致重试，反而更久。这是 6.6 里"连续 10 分钟不断流"
比"峰值速率"更该测的原因。真遇到带宽极差（总带宽 <4Mbps），服务端按 `op` 顺序给每台错开 3 秒启动，
避开 AP 队列拥塞，代价是最后一个晚 12 秒开始——仍在 5 分钟内。

## 5. 终端本地存储（决定 A2/A3/A4/A8 能不能过）

### 5.1 目录结构：只有一个 current

```
%LOCALAPPDATA%\esop-client\
  config.json    {op, server, kiosk, autoStart}
  content\
    index.json   当前这套内容的索引 {modelCode, modelId, seq, items:[{mediaId,ext,kind,dwellSec}]}
    current\     正在播的那一套，文件名 <mediaId>.<ext>（mediaId 就是 sha256 前 16 位）
  logs\terminal.log
```

- `current\` 就是**唯一在播的那一套**，任何时刻只对应一个（机种 × 工序）
- 目录名**不带型号**：型号改名、中文、特殊字符都不会引发路径问题
- `index.json` 是唯一索引；损坏或与 `current\` 不符 → 按"无内容"处理重拉。**不做自动修复**，因为重下只要几秒
- 磁盘常态占用 **约 27MB**。超过 60MB 就说明有旧文件没删干净——这是 A8 最直观的判据
- `config.json` 优先生效的是 **exe 同级目录**那份（运维批量改它最方便），启动时同步一份到本目录

### 5.2 翻转那一下，文件怎么换（实现修正，与 v0.4.0 不同）

v0.4.0 写的是"目录三步 rename：`current → old_<ts>`，`tmp → current`"。**实机做不出来**，改为
**文件级共存 + 精确删除**。原因是 exe 里停播和换目录分属两个进程：

- 目录 rename 必须等渲染层真的把 `<video>` 关掉才可能成功，而这段等待就是一个**可测量的黑屏窗口**，直接违反 A2
- 跨进程的"停 → 改 → 起"没有原子性可言，中间任何一步失败都会留下一个既不是新也不是旧的目录

现在的做法（`terminal/src/cache.js`）：

```
① 新文件下到 current\，先写 <mediaId>.<ext>.part
② 边下边算 sha256，校验通过才改名成 <mediaId>.<ext>（文件名不同，天然不覆盖旧文件）
③ 新内容在隐藏层预载完成 → 渲染层一次性切换可见层（双缓冲，零黑屏）
④ 渲染层 ack → 主进程写 index.json → 删掉"不在新清单里"的文件
```

三件事因此成立：

| A2 / A4 的底线 | 翻转成功之前，旧文件一个都没动。断电、断网、切换失败都毁不掉正在播的内容 |
|---|---|
| A8 | 翻转后按新清单精确删除，稳态下目录里只有当前一套；连切 3 次文件数不增长 |
| A9 | 渲染层换队列是一次同步调用（`flip`），中间没有 `await`，队列和画面一起变 |

**`.part` 的意义**：正式文件名只代表"完整且校验过的内容"。因此"文件存在"就可以跳过下载，
连点三次切换也不会重复拉同一个文件。启动时把所有 `.part` 直接删掉重下——
判断"哪个下完了"的成本比重新下 27MB 高。

**删不掉怎么办**：Windows 上 `<video>` 或缩略图缓存占住文件时 `EBUSY/EPERM` 是常态。
进 `pendingPurge` 队列 → 60 秒后重试 → 启动时再扫一遍 → 连续失败记日志。
**不做静默跳过**，否则磁盘会在几周后悄悄堆满旧型号。

### 5.3 首次装机与冷启动

新机器第一次开机本地什么都没有，走"自补内容"路径，与切换共用同一套下载代码：

| 时刻 | 动作 |
|---|---|
| 开机 → 长轮询 | 拿到 `idle` + `modelCode`；判断依据是"本地有没有这个型号"，不看 `phase` |
| 本地没有 → 直接下载 | 顶栏 `正在获取内容 3/11`，中间显示等待页 |
| 下完 → flip | 起播 |
| 若此时服务端正在 prepare | 优先下 `pendingModel`，避免"刚下完旧的又被换掉" |

**等待页不能是纯黑**：全新机器黑屏几秒，现场会以为机器坏了。显示型号 + 工序 + 进度条 + "正在获取内容"。

### 5.4 离线兜底

| 场景 | 结果 |
|---|---|
| 断网，`current\` 有内容 | ✅ 照常循环播放，顶栏 `离线`（灰，不打扰）。这就是 A4 的全部实现 |
| 断网，本地无内容（新机器） | 显示等待页 + 每 10 秒重试，画面不闪不跳 |
| 断网时点了切换 | 终端收不到指令（服务器也在同一 AP 后面），网络恢复后自动补。**不测这个场景**，见 A3 口径 |

播放本身在物理上不依赖网络——文件都在 `current\` 里。**网络只影响下载那一段**，这是 6.7 里
"要求从 50Mbps 降到 90KB/s"的根本原因。

### 5.5 服务端媒体回收

媒体是内容寻址的，多个（机种 × 工序）可能引用同一个 sha。所以**服务端不能跟着终端一起删**：

- 终端删自己的 `old_<ts>\`，与服务端完全解耦，互不通知
- 服务端的 `POST /api/media/gc` 只删"`item` 表里零引用"的媒体
- 工程部把某张图从所有清单移除后，该文件**不会自动消失**，需手动点 GC 或等每日定时任务

> 为什么不自动：工程部编辑清单时会有中间态（刚删了又加回来），自动 GC 会误删正在用的文件。
> 手动/定时是安全的，代价是磁盘暂时多占几 MB——可接受。

## 6. 接收端（Electron exe）

### 6.1 进程结构（已实现，`terminal/`）

```
main.js            窗口 / kiosk / 看门狗 / 自启 / 托盘 / 快捷键拦截
 ├─ src/config.js   config.json 读写，路径全 ASCII（%LOCALAPPDATA%\esop-client）
 ├─ src/net.js      长轮询、下载（边下边算 sha256）、POST
 ├─ src/cache.js    磁盘内容：.part → 校验 → 正式名；index.json；精确删除 + pendingPurge
 ├─ src/sync.js     同步状态机：长轮询 → prepare 下载 → 举手 → 等 activate → 通知翻转
 ├─ preload.js      只暴露 6 个方法（snapshot / onView / onStatus / flipped / log / 设置页那套）
 └─ renderer/       player.html（播放）+ setup.html（装机向导）
```

**主进程独占网络与磁盘，渲染层只看 file:// 路径。** 两个理由：

- exe 加载的是本地页面，`file://` 去 fetch 服务器是跨源；而且断网时页面若从 http 加载，连界面都起不来，A3/A4 直接不成立
- Node 侧才能边下边算 sha256、才能直接写文件

**窗口约束**：kiosk + 无边框 + 置顶 + `backgroundThrottling:false`（失焦不降频，否则翻页会卡）。
拦截 F11/F12/F5、Ctrl+R/W/N/P/O/U、Ctrl+Shift+I/J/C、Alt+F4；右键菜单与 `will-navigate` 一律禁掉。

**看门狗**：每 10 秒读一次 `window.__vwiBeat`（页面每秒打点），连续 3 次读到「太旧/读不到」就 reload。
`unresponsive` 与 `render-process-gone` 也各自兜一次，避免白屏挂在那里没人知道。

**开机自启**：`app.setLoginItemSettings({openAtLogin})`，开发模式不写（否则注册的是 electron.exe）。

**维护逃生门**：`Ctrl+Alt+Shift+Q` 直接退出。kiosk 下任务栏可能被置顶窗口盖住、托盘点不到，
没有这个组合键就只能拔电源或开任务管理器。托盘菜单另给了「重新同步内容 / 打开内容目录 / 打开日志 / 更改设置」。

**配置优先级**：exe 同级 `config.json` > `%LOCALAPPDATA%` 里的那份。前者存在时会覆盖后者并同步一份过去——
这样"改部署包里的 config.json 再重启"就能换配置，不用进程序点。缺配置不黑屏，弹装机向导（探服务器 → 选工序 → 保存）。

### 6.2 渲染进程（播放器）

- **固定设计稿 1280×1024**，用 `transform: scale()` 适配任意实际分辨率。不做响应式——5:4 屏上响应式必错，缩放最稳。
- 播放单元只有两种：`<img>` 与 `<video>`。预加载下一张图（避免闪白），视频播完即下一项。
- 图片默认停留 **10 秒**（可按项调整），视频播完自动下一项。
- 切型号**不重载页面**，只替换播放队列并回到第 1 项——重载会闪白，违反 A2。
- 单条内容出错（图裂、视频解码失败）跳过并在角落记录，不卡死整个循环。
- **内容不全**（清单项数 < 服务器报告应有数）→ 照播，顶栏挂橙色 `内容不全 8/11`，不静默
- **切换准备中**（prepare 阶段下载中）→ 画面照旧播旧内容，顶栏挂蓝色 `正在切换到 X400 · 3/11`，**绝不切一半**
- **掉队未就绪**（超时强翻但它没备完）→ 顶栏红字 `内容未就绪 · 请勿作业` + 边框闪烁，翻完自动消失
- 翻页是同步函数（见 4.4），渲染层不感知"切换中"这个中间态；中间态只存在于下载准备阶段

### 6.3 界面（1280×1024，三区）

┌──────────────────────────────┐  0
│ 顶栏 88px    X300 · OP30   ● │  型号 + 工序 + 在线点
├──────────────────────────────┤  88

| 风险 | 概率 | 对策 |

| 19 寸屏实际是 1366×768 | 中 | 播放器读实际分辨率，设计稿等比缩放；内容规格不变 |

## 11. 内容模型与界面数据流（v4.0.0：机种 × 工序）

### 11.1 「该交什么」由工序自己表达（配置库、工位层都已退役）

```
机种 X200
  ├─ 可生产线体：一线、二线（model_line，只是"C 位"关系，没有内容）
  └ 工序 OP1 装配
       ├── process_req  图片/视频/PDF 各自"至少几份"、图片最小分辨率
       ├── play_mode    loop 循环播放 / once 播一遍停
       └── item         实际内容清单（有序，带停留秒数、适应方式、缩放）
```

**为什么内容只存一份**：同一个机种排到哪条线，做的都是同一套工艺 —— 装配还是装配、检验还是检验。
v3.0.0 为了兼容"两线工序码含义不同"把内容按线拆开，代价是每个机种在每条线都要配一遍，
两条线四个工位里三个是空壳。现场确认过工艺不随线变，所以这一层拆掉。

**换线怎么处理**：机种设置里把线勾上即可，内容不动 —— 本来就共用。真有个别线工艺不同，
就给那个机种加一道专属工序（`OP30-2` 之类），工序码允许横线和数字。

**旧方案的坑**：v1.8.0 引入 `profile`（配置档案）作为独立一层，图的是"模板与内容解耦"——
改模板不能动内容、删模板不能删内容。目标没错，但实现上要维护一套
"档案 ↔ 机种 ↔ 线体"的匹配规则（绑机种 → 编码带机种号 → 绑线体 → 通用档案 → 匹配不到），
现场一半机种没建档就什么都不显示，运维根本不知道该填什么。

**v2.0.0 起的做法**：既然内容挂在工序上，"该交什么"就长在同一个工序行上——
`process_req` 是 `process` 的子表，一对一，没有任何匹配规则要算。

| 语义 | 实现 |
|---|---|
| 这道工序允许放图片 / 视频 / PDF | `process_req` 里有对应 `kind` 的行 |
| 至少几份 | `min_count` |
| 图片最小分辨率 | `min_width` / `min_height` |
| 整张 reqs 表为空 | 视为**未配置**，不做类型锁 |
| 怎么播 | `process.play_mode`（`loop` / `once`） |

**"没配置"不等于"不合格"**：reqs 为空时上传不受限、界面不显示红字。
新建机种铺出的工序默认只允许 1 张图片，不会出现"全厂都标红"。

闸门只有一处（`saveProcess()`），`PUT /api/processes/:id` 与上传入口共用：
校验不通过整批不动，不会出现"删了旧图、新图没插进去"的半套状态。

**为什么是整批覆盖而不是逐条增删**：内容与要求一次 `PUT` 提交，
前端先整批校验、后端事务内先删后插。逐条调用会有中间态——删了旧、新还没插的窗口里，
终端正好来拉清单就会拉到半套。整批覆盖没这个窗口。

### 11.2 界面每个区域的数据来源

界面骨架：**左侧功能区 + 右侧内容区**。
左栏只回答"我要干什么"；「作业内容」是**总览**，其余各项都是**设置**页。

| 区域 | 数据来源 | 刷新 | 作用 |
|---|---|---|---|
| 左栏功能区 | 静态 | — | 作业内容 / 线体设置 / 机种设置 / 媒体库 / 文件查询 / 终端监控 / 系统 |
| 总览 · **产线概览** | 同上 `overview` | 同上 | 五个数字：总数 / 运行中 / 停用 / 维修中 / 保养中（只数线体状态，不掺在线数） |
| 总览 · **运行产线行** | 同上 `lines[]`（只取 `status = running`） | 同上 | 一行一条：当前机种（标亮）/ 下一个机种 / 换型进度 / 在线数 |
| 总览 · **排产** | `POST /api/board/next` | 点「+ 排产下一个机种」→ 选机种 → 确定 | 只记 `next_model_id`，不动终端；`✕` 传空值取消 |
| 总览 · **换型** | `POST /api/board/switch` | 点「换型」 | 取该行 `nextModelCode` 下发；换型一开始 `next` 就被清空（进了 `pending`） |
| 线体设置 · 线体表 | `GET /api/lines` | 载入、切视图 | 六列：名称 / 工位数 / 可生产机种 / 状态 / 在线 / 操作 |
| 线体设置 · **状态四键** | `PUT /api/lines/:id {status}` | 点哪个亮哪个 | 运行 / 停线 / 维修 / 保养 就地切；从运行改成别的要二次确认 |
| 线体设置 · 可生产机种 | `GET /api/lines` 的 `modelCodes` | 随 `/api/models` 变 | 点数字看这条线能做哪些机种（自动统计，不能手填） |
| 线体设置 · 新建 / 修改 | `POST /api/lines` / `PUT /api/lines/:id` | 点按钮 | 只问名称、工位数、状态；编码自动生成 `L1/L2…`（修改弹窗里可改） |
| 机种设置 · 机种胶囊 | `GET /api/models` | 载入、改完 | 每个胶囊：编码 / 名称 / 关联线体 / `已配/总数` |
| 机种设置 · **新建机种** | `POST /api/models` | 点「+ 新建机种」 | 编码 / 名称 / 几道工序 / 可生产线体多选 → 一次铺 `OP1…OPn` |
| 机种设置 · **工序表** | `GET /api/processes?modelId=` | 载入、改完一格 | 一行一道工序：工序码（只读）/ 名称 / 做什么 / 播放方式 / 内容数 |
| 机种设置 · 就地编辑 | `PUT /api/processes/:id` | 离开单元格（`change`） | 只提交 `{name}` 或 `{note}` 或 `{playMode}`，**不碰 reqs 与 items** |
| 机种设置 · 导入 Excel | `POST /api/import/parse` → `POST /api/processes/import` → 可选 `/import/undo` | 选文件后 | 先逐行判定给预览，确认了才按 `merge` / `update` / `update-only` 批量写；导错了按批次撤销 |
| 机种设置 · 导出 / 模板 | `GET /api/export/processes.xlsx` / `GET /api/export/template.xlsx` | 点按钮 | 全厂一张表（四列），改完能整份导回 |
| 媒体库 · 机种下拉 | `GET /api/models` | 切换 | 只有机种一级 —— 内容不跟线走，再选线体是多余的一步 |
| 媒体库 · **工序索引** | `GET /api/processes?modelId=` | 切机种 / 保存后 | 三色圆点 + `已配/总数` + 进度条 + 筛选 + 搜索 |
| 媒体库 · 工序卡 | 同上 | 选中即渲染 | **只渲染 1 张**：允许类型、体积上限、播放方式、内容清单、排序 |
| 媒体库 · 上传 | `POST /api/media/upload` → `PUT /api/processes/:id` | 拖入即传 | 先传媒体（sha 去重），再整批保存这道工序的内容 |
| 文件查询 · 文件网格 | `GET /api/media` | 载入、搜索、筛类型 | 全库文件与被引用次数 |
| 文件查询 · 体检 / 清理 | `POST /api/media/advice` / `POST /api/media/gc` | 点按钮 | 规格体检、清理未引用 |
| 系统 · 版本与地址 | `desk.info()`（桌面程序 preload 桥） | 切到该页 | 版本 / 端口 / 局域网地址 / 数据目录 / 自启；浏览器版没有此项 |
| 终端监控页表格 | `GET /api/terminals` | **每 2 秒** | 每台屏一行：IP / 分辨率 / 版本 / 磁盘 / 进度 / 状态 |
| 左下角状态 | `/api/status` 的 `online` + `version` | 长轮询 | 在线台数 / 版本号 |

**为什么媒体库只选机种**：内容挂在工序上，工序又挂在机种上，线体在这条链上不出现。
v3.x 那会儿必须先选线体，是因为内容真的按线分；现在让现场多点一次、还可能点错
（"我在二线上配的，怎么一线上没有？"）没有意义。

**为什么线体编码不出现在表里，只放在「修改」弹窗**（v4.0.0）：编码是终端 `config.json`
里寻址用的（`L1`、`L2`），现场每天看的是"一线今天在跑什么"。摆在表里既占宽度又要人想
"这个能不能改"。默认自动生成，真要改进去改 —— 弹窗里写明"终端装机要填这个"。

**为什么工位数只做展示、不做校验**：它代表"这条线实际有几块屏"，是物理事实；
工序数是"这个产品有几道工序"，是工艺事实。两者应当匹配，但**不该用红字拦着人干活**——
新线还没装满屏、临时借一块屏调试，都会被拦。所以只在机种页给一条黄色提示
「工序数超过线体工位数」，看一眼就知道，改不改由人。

**为什么把"定义"和"内容"拆成两页**（v3.2.0）：一页里同时放着"这道工序做什么"
和"这道工序放哪些图"，改名字要在一张卡里上下找，传文件又要滚回拖放区 —— 两件事的心思
根本不在一个层面上。拆开之后：

| 页面 | 只回答 | 数据 |
|---|---|---|
| 机种设置 | 这个机种**有哪些工序、各做什么、怎么播** | `process.code/name/note/play_mode`（表格就地改） |
| 媒体库 | 这道工序**放什么文件** | `process_req` + `item`（含允许类型、体积上限） |
| 文件查询 | **全库有哪些文件** | `media`（体检、清理未引用） |

拆得干净的关键在于**接口本来就支持**：`saveProcess()` 里 `name` / `note` / `maxMb` /
`playMode` / `reqs` / `items` 是六块各自判断 `!== undefined` 的独立更新，所以机种设置只提交
`{name, note}` 或 `{playMode}`、媒体库只提交 `{reqs, items}`，谁也不覆盖谁。

**「允许类型」和「播放方式」为什么都在媒体库**：它们只影响"怎么放"，跟工序叫什么无关 ——
上传时立刻要知道能不能放视频，播的时候立刻要选循环还是一次。放在上传按钮旁边，
比放在另一页的表格里少一次来回（机种设置的工序表里也留了一份，两处改的是同一个字段）。

**工序码为什么在表格里只读**：它建机种时定下（`OP1…OPn`），终端按 `?op=OP30` 找内容 ——
码一改，那块屏的 `config.json` 就指空了。所以界面上不给改码，只给加减工序；
真要换码，加一道新的、把内容挪过去、删掉旧的（比暗中改码安全）。

**为什么导出和导入共用一个表结构**（v3.4.0 起）：3.3.0 的导出是「每个机种一个工作表」，
可导入只读第一页 —— 导出来的文件改完根本传不回去，导出和导入成了两套东西。
现在导出就是**全厂一张表**：四列 `机种 / 工序码 / 名称 / 做什么`，模板与它逐列同构，
于是「拉下来 → 改 → 传回去」是一条真闭环，而不是两个功能各自长得像。
4.0.0 又把「线体」这一列去掉（内容不跟线走了），五列老文件仍然能导 —— 那一列被识别但忽略。
代价是丢掉了「一个机种一张表」的排版，但那张表本来也只能看不能改回来。

**为什么认表头名不认列号**：工艺表是各人各做的，最常见的一种是在模板前面插一列「序号」，
或者把「做什么」挪到名称前面。按位置读（0/1/2）整表就错位了，而且**错得没有报错**——
工序码列读到了序号，几十行全是 `1、2、3`。别名表收的是表头写法（`工序号 / 工序名称 / 工序内容 /
备注` 这些），识别不出才退回按位置读。「序号」列**故意不收**，它就该被忽略。

**为什么表里带「机种」列就按行分流**：全厂一张表必然一列装不下一个机种，所以每行自带归属。
文件里有「机种」列走「全厂模式」，按行分到各自机种；没有就导到界面当前选中的那一个 ——
3.3.0 的三列表不用改就能继续导，不用逼着现场重做一遍模板。

**为什么未建档的机种不自动建**：夹具系统是自动补建的（产线就是一张平坦清单，
补错了删掉即可），但这里的机种是**产品档案**，凭空多一个「X200 型2」
会连出一整套空工序，还要人去媒体库逐个删。宁可拦住并告诉你「机种 X9999 还没建档」，
补建之后再导一次。

**为什么三种模式而不是两种**：`merge`（只加新的）用于补工序；`update`（加新的 + 更新有变化的）
用于价格/工艺变更后整表刷新；`update-only`（只改不建）用于表里混了草稿行时、
只想把现有工序的名字改一遍。内容一模一样的行算 `kept` 不重写库 ——
重复导同一份表对库零影响，这一点靠的是逐行跟库里比对，不是靠"看起来一样"。

**为什么撤销只删新建、不回滚改名**：新建的行有 `import_batch` 认得出，删了干净；
改名/改说明的旧值**没留底**，硬编一个"还原"要么得整表存快照（几十 MB），
要么就得猜，猜错了比不还原更麻烦。所以撤销的语义是「把这次多出来的行收回去」，
不是「把库退回到导之前」。

**为什么总览单独一个接口 `GET /api/board`**：总览要同时回答"几条线、各做什么机种、哪几块屏切完了"。
如果让前端先拉 `/api/lines`、再逐线拉 `/api/terminals`、再拉 `/api/models`、再逐格拉清单，
开一次页面就是十几个请求，中间任何一步慢都会让卡片闪烁重排。一次返回整张看板，结构稳定。

**为什么「作业内容」从"每线一张卡"改成"一行一条线"**（v3.5.0）：卡片里塞着当前机种、
五颗工序胶囊、缺内容告警、换型下拉，一屏放不下三条线。而这一页每天被问的只有四件事：
今天几条线在跑、每条线做什么、下一个做什么、换型点到哪一步。工序层面的细节（哪块屏、
什么状态）属于「线体设置」和「终端监控」，堆在总览里反而看不清主线。

**为什么 `line` 要同时有 `enabled` 和 `status`**：`status` 是给人看的四态
（运行中 / 停用 / 维修中 / 保养中），`enabled` 是给机器看的开关（只有 `running` 才为 1）。
冗余是故意的 —— 终端协议、`switch.js`、`activeLine()` 全都读 `enabled`，
加 `status` 不用改它们一行；迁移时按 `enabled` 回填，老库无感。
**回填语句必须写在"加列"那个 `if` 里面**，放外面每次启动都会把"维修中"刷回"运行中"。

**为什么放开"同一时刻只允许一条线启用"**（v3.5.0）：那条限制是为了**不带 `line` 参数的老终端**
能唯一确定听谁的。现在现场每条线有自己的终端、各自带 `?line=L1`，限制反而挡住正事 ——
两条线同时开工是最常见的排产方式。放开后老终端的回落规则变成"**sort 最前的启用线**"，
行为确定、不报错。副作用一处：以前"启用二线"会顺带清掉一线的在线记录，
现在不会 —— 一线有几块屏在线就是几块，换型要它们都举手才激活。

**为什么「下一个机种」要单开一个字段**：`pending_model_id` 是"**正在切**"，
切完就清，中途放弃要回滚；`next_model_id` 是"**排好了、还没开始切**"，可以放这儿过夜。
两者混用会出现"排产把换型顶掉"或"放弃切换后凭空冒出一个待办"。
点「换型」时 `next` 直接进 `pending` 并清空自己 —— 中途放弃的话排产就没了，
比留一条和 `pending` 打架的数据干净。

**为什么 `/api/board` 里每道工序都占一个客户端位**：没装机的屏也要列出来（`absent`），
否则运维看不出"这条线本该 5 块屏、实际只上线了 3 块"——那才是最需要发现的问题。

**为什么终端详情要独立成页**：IP、分辨率、磁盘挤在总览卡片里必然要截断（`1920×10…`），
5 台屏一眼扫不完。总览卡片只放状态色和"没内容"标记，细节去终端监控页看。
**为什么右栏单独 2 秒轮询、不走长轮询**：长轮询是"等变化"的语义，25 秒才回一次；
把下载进度塞进长轮询的 `rev`，等于每 2 秒把全厂终端的"耳朵"叫醒一遍。
所以 `/api/telemetry` 和 `/api/terminals` 都是**不 bump rev** 的旁路数据：
它只影响那两张表格，不影响任何业务判断。

### 11.3 终端的机器参数怎么来

```
终端启动         main.js collectMeta() → screen.getPrimaryDisplay() × scaleFactor（物理像素）
                                       → fs.statfsSync(内容目录) 剩余空间
每 5 秒          POST /api/telemetry  { res, ver, free, done, total, model, st }
长轮询每次       GET /api/state?op=…&res=…&ver=…&free=…   （老终端不改代码也够用）
服务端           touch(line, op, meta) 合并进内存档案，IP 由 socket 取，不信自报
管理端           每 2 秒 GET /api/terminals
```

- 参数**不落库**：重启丢掉无所谓，下一轮心跳就补回来；落库反而要处理过期清理。
- 离线档案保留 30 分钟：用来区分"从未上线"（`seen=false`，多半没装机）和
  "已离线 5 分钟"（关了机）。现场问"3 号工位怎么没数据"，答案就在这个区分里。
- 1.6.0 之前的终端不上报这些字段，界面显示「—」，不影响换型与下发。

### 11.4 展示逻辑上的几条约定

| 情况 | 界面表现 | 为什么不做得更"友好" |
|---|---|---|
| 线的某个工序从来没终端连过 | 表格一行 +「从未上线」 | 空着会让人以为是加载中 |
| 终端在线但内容还在下 | 进度条（蓝）+ `X300 3/7 项` | 只显示"准备中"看不出还剩多久 |
| 已举手 | 进度条转绿 +「已就绪」 | 和"在线"必须能分开，否则没法判断能不能翻 |
| 内容项数够但分辨率不达标 | 格子写"规格不符"，抽屉逐项标红并写清 `8×8 低于 1280×720` | 只说"不合格"等于让人自己一张张量 |
| 看的是未启用的线体 | 页面顶部黄条 + 「设为启用」按钮 | 不提示的话，人会以为终端坏了 |
| 机种没匹配到配置 | 不显示要求 | 没配置 ≠ 不合格 |
| 上下文条上点了别的线体 | 只切"看哪条"，**启用状态不动** | 浏览内容时误触勾选框 = 整线停产 |
| 想启停某条线 | 得去「线体设置」页 | 同上：启停是"低频且有后果"的操作，不该放在浏览路径上 |

### 11.5 视觉规范：与工装夹具管理程序（FMS）一致

v1.10.0 起管理端换皮为 FMS 那一套（深色侧栏 + 白顶栏 + 浅底白卡片），
现场在两套系统之间切换不用重新适应。

| 元素 | 取值 |
|---|---|
| 侧栏底色 | `#0f172a`，导航项 `#94a3b8`，选中 `#2563eb` |
| 页面底色 | `#f4f6fb` |
| 卡片 | `#ffffff` + `0.5px #e5e7eb` + 圆角 10px + 轻投影 |
| 主色 | `#2563eb` |
| 成功 / 警告 / 危险 | `#16a34a` / `#d97706` / `#dc2626` |
| 左下角 | 版本号 + `design by Frank, 2026.10` |

**左栏是纯功能区**：六个入口在所有页面长得一模一样，切换功能时不需要重新找"东西在哪"。
线体这种"当前作业对象"归内容区顶部的上下文条管 —— 这是这次重构的核心判断：
**功能与上下文混在一列里，人就得靠位置去猜自己正在做哪类操作。**
