## 0. 一页结论

| 项 | 决定 |
|---|---|
| 服务器 | 一台 Windows 电脑，Node 22 + **内置 SQLite**，零 npm 依赖 |
| 接收端 | Electron exe，1280×1024 设计稿 + 缩放，kiosk 全屏 + 开机自启 + 看门狗 |
| 层级 | **型号 → 工序 → 清单**，到此为止，无工位 |
| 终端身份 | 启动参数 `?op=OP30`，只此一个值，不注册不建档案 |
| 切换通道 | **长轮询**（挂 25 秒）+ 30 秒兜底，不用 WebSocket/SSE |
| 内容存储 | `media/<sha256前16>.<ext>` 内容寻址，天然去重 |
| 切换语义 | **两段式原子切换**：`prepare` → 全员 `ready` → `activate`，5 台同帧翻 |
| 终端缓存 | **单套**：只有当前型号 × 本工序 ≈ **27MB**，切完即删 |
| 切换耗时 | 正常 **3–6 秒**；验收上限 **5 分钟**；掉队超时强翻 + 告警 |
| 数据表 | **5 张** |
| 接口 | **13 个** |

一句话：**服务器存内容、记一个"现在做哪个型号"；换型时先喊大家去下载，5 台都下完了再一起喊翻，翻完各自删掉旧文件。终端盘上永远只有一套内容。**

## 2. 数据模型（5 张表）

```sql
-- 产品型号
model   (id, code UNIQUE, name, enabled, sort)

-- 工序：5 条固定记录，也是终端唯一的身份
process (id, code UNIQUE, name, sort)

-- 媒体：内容寻址，同一文件只存一份
media   (id PK = sha256 前 16 位, sha256, kind 'image'|'video',
         ext, bytes, width, height, duration_ms, created_at)

-- 播放清单项：(型号 × 工序) 下的一条
item    (id, model_id, process_id, ord, kind, media_id,
         dwell_sec, UNIQUE(model_id, process_id, media_id))

-- 全局状态：KV，4 把钥匙
setting (key PK, value)        -- current_model_id / seq
                               -- pending_model_id / pending_deadline（切换进行中才有）
```

**为什么 `setting` 就够**：换型是全网统一的，服务端只需记住"现在做哪个型号"（`current_model_id`）和一个单调递增的 `seq`。
两段式切换进行中时，额外落库 `pending_model_id` + `pending_deadline` 两个值，让服务重启后能把这次切换接着推进
（终端会重新举手，因为下载进度在终端本地）。

**举手名单（ready）不落库**，放内存 `Map<op, {seq, readyAt}>`：重启后清空，各终端下一次 `POST /api/ready` 会重新补上。
丢一次举手名单的代价只是"多等几秒"，而落库反而要处理过期清理，不划算。

**刻意不建的表**：`station`（已取消）、`user` / `session`（不做权限）、`release`（不做版本治理）、`play_log`（不做统计报表）、`page` / `block`（不做版式）、`switch_log`（切换记录写进程日志即可）。

## 3. 接口（13 个）

| # | 方法 | 路径 | 说明 |
|---|---|---|---|
| 1 | GET | `/api/models` | 型号列表，带**内容完成度**（50 套里齐了几套） |
| 2 | POST / PUT | `/api/models[/:id]` | 新建 / 改名 / 停用 |
| 3 | GET | `/api/processes` | 5 道工序 |
| 4 | GET | `/api/playlist?modelId=&processId=` | 管理端取某型号某工序的清单 |
| 5 | PUT | `/api/playlist` | **整批保存**（一次提交该工序全部项，避免逐条增删的中间态） |
| 6 | POST | `/api/media/upload?filename=&kind=` | 流式上传，返回 sha 与宽高 |
| 7 | GET | `/api/media` | 媒体库（带被引用次数） |
| 8 | POST | `/api/media/gc` | 清理无引用媒体 |
| 9 | POST | `/api/switch` | **核心**：`{modelCode}` 发起切换（进 prepare，**不立即生效**） |
| 10 | POST | `/api/ready` | 终端举手 `{op, seq}`：本工序内容已备齐并校验通过 |
| 11 | GET | `/api/state?since=<seq>` | **长轮询**：`{seq, phase, modelCode, deadline, online[], ready[]}` |
| 12 | GET | `/display/playlist?op=OP30&model=X300` | 拉**指定型号**本工序的清单与媒体地址 |
| 13 | GET | `/m/:id` | 媒体文件，支持 Range |

管理界面本身是静态文件，不占接口。

**终端不鉴权**：只带 `op` 参数，没有令牌。因为一期没有权限体系、只部署在内网，工序代码也不是秘密。
代价是内网任何人能拉到内容——可接受，但**服务器绝不能直接暴露到办公网或外网**。

## 4. 切换协议（决定 A1 / A9 能不能过）

### 4.1 两段式：prepare → ready → activate

服务端只有一个三相状态机，没有别的：

| phase | 含义 | 进入方式 |
|---|---|---|
| `idle` | 稳定在某型号，大家正常播 | 初始 / activate 之后 |
| `prepare` | 正在让全线下载新型号，**尚未生效** | `POST /api/switch` |
| （内部）| 收齐举手，或到 5 分钟 | 服务端自己判断，然后 activate |

**第一段 `POST /api/switch {modelCode}`**——注意这里**不动 `current_model_id`**，所以工人看不出任何变化：

```sql
BEGIN;
  UPDATE setting SET value = :targetModelId       WHERE key = 'pending_model_id';
  UPDATE setting SET value = :now + 300000        WHERE key = 'pending_deadline';
COMMIT;
-- 唤醒所有挂起的长轮询 → phase='prepare'
```

**第二段**：终端下完各自 `POST /api/ready {op, seq}`。服务端每收到一个就检查一次：

```js
function maybeActivate() {
  if (phase !== 'prepare') return;
  const onlineOps = [...online].filter(o => Date.now() - o.lastSeen < 60_000).map(o => o.op);
  const allReady  = onlineOps.every(op => ready.get(op)?.modelId === pendingModelId);
  if (allReady || Date.now() >= pendingDeadline) activate();
}
```

`activate()` 才真正改状态：

```sql
BEGIN;
  UPDATE setting SET value = (SELECT value FROM setting WHERE key='pending_model_id')
   WHERE key = 'current_model_id';
  UPDATE setting SET value = CAST(value AS INTEGER) + 1 WHERE key = 'seq';
  DELETE FROM setting WHERE key IN ('pending_model_id','pending_deadline');
COMMIT;
-- 唤醒长轮询 → phase='idle' + 新 modelCode + 新 seq
```

**三个关键判断，都有代价在背后**：

| 决定 | 为什么 |
|---|---|
| **分母用"在线终端"而不是常数 5** | 某台屏今天没开机、或只装了 3 台，用 5 做分母就永远等不齐，每次都要拖到 5 分钟。分母取"最近 60 秒有过请求的 op" |
| **超时也强 activate，不无限等** | 一台网络烂就全线停产，这比"个别屏晚一点"严重得多。掉队的那台见 4.4 的告警 |
| **`seq` 只在 activate 时 +1** | prepare 期间 `seq` 不变，终端不会误判"要翻了"。这是"准备中"和"已切换"在协议层的分界 |

`GET /api/state?since=N`：
- `seq > N` → 立即返回 `{seq, phase, modelCode, deadline, online, ready}`
- 否则挂起，最多 25 秒；超时返回当前值（让终端确认链路活着，同时兼作心跳）
- **prepare 期间即使 `seq` 没变也要返回**（因为它带 `phase` 和 `deadline`），否则终端永远不知道要开始下载

`online` 来自内存 `Map<op, lastSeenAt>`，随每次 `/api/state` 与 `/display/playlist` 刷新，**不落库**；`ready` 同理。
服务重启后 30 秒内随终端心跳自动重建——代价只是重启那一次切换可能提前 activate，可接受。

**为什么"等齐了才喊"就是"一起切"**：5 台终端挂的是同一条长轮询，`activate()` 后遍历挂起表逐个 `resolve`，
在同一个事件循环 tick 里完成，彼此间隔**微秒级**。真正决定"齐不齐"的是前面的举手机制，不是这最后一下广播。

### 4.2 终端：一个循环，三个分支

终端只保存两个值：`appliedSeq`（已生效的 seq）和 `localModel`（本地盘上现在是哪个型号）。

```
loop:
  r = GET /api/state?since=appliedSeq          (25 秒超时)

  ── 分支① 准备中 ──────────────────────────────
  if r.phase == 'prepare' && r.pendingModel != localModel && 当前没在下载它:
      startDownload(r.pendingModel)             // 画面照旧播旧内容，顶栏挂"准备中 3/11"

  ── 分支② 该翻了 ──────────────────────────────
  if r.phase == 'idle' && r.seq > appliedSeq:
      if 本地已备好 r.modelCode:
          flip(r.modelCode)                     // 同步翻（见 4.4）
          appliedSeq = r.seq
      else:
          掉队：保持旧画面 + 顶栏红字告警，继续下载，下完再自己翻（见 4.4）

  ── 分支③ 其余 ────────────────────────────────
  什么都不做（超时心跳，顺便刷新 online）
```

**关键设计：状态机而不是命令队列。** `seq` 表达"现在应该是什么型号"，不是"请执行第 N 号命令"。
所以班长连点三次 X300 → X400 → X300：

- 终端①次收到 prepare X300，开始下
- 第二次收到 prepare X400 → **取消 X300 的下载**，改下 X400（`pendingModel` 变了）
- 第三次回到 X300 → 再取消再重下

只有中间态被跳过，最终必然收敛到 X300。**不会出现"翻到 X400 停 200ms 再翻回 X300"的闪动**，这是 A9 的保证机制。

> 取消重下会浪费已下的流量，但"连点三次切换"本身就是误操作，不是常态。
> 优化它（比如保留已下完的文件做增量）会把逻辑复杂度翻倍，不值得——27MB 重下只要几秒。

### 4.3 下载与校验：先落 tmp，校验通过才换指针

| 步骤 | 动作 |
|---|---|
| 1 | `GET /display/playlist?op=OP30&model=X400` → 清单（每个媒体的 id、sha、字节数、停留秒数） |
| 2 | 建临时目录 `tmp/<modelId>/`，逐个下载 |
| 3 | 每下一个就校验 sha256；不符 → 删掉重下一次；再不符 → 记"缺失"继续下一个 |
| 4 | 顶栏实时更新 `准备中 3/11`（每完成一个 +1） |
| 5 | 全部完成（含"缺失"降级）→ `POST /api/ready {op, modelId}` |
| 6 | 等 activate 推过来；若已被超时强 activate，自己下完后自愈翻页 |

**为什么下到 `tmp/` 而不是直接覆盖当前目录**：切换失败、中途断电、网络断了换回原型号——
任何一种情况下，**旧内容必须完好无损**。这是 A2（不黑屏不闪白）和 A4（断网 8 小时不断播）的底线。
tmp 下完且校验通过后，才在 flip 那一刻把目录指针换过去。

**为什么单文件串行，不并发**：5 台终端 × 每台多文件并发，会把 AP 队列打满，正在播的视频直接卡顿。
27MB 串行在 1Mbps 下也就 3.6 分钟，稳稳落在 5 分钟窗口内。**用并发度换"播放不受影响"，这笔交易值。**

**下载中断怎么办**：断电/断网后重启，`tmp/` 里可能留半截文件。启动时**整个 tmp 目录删掉重下**——
判断"哪个文件下完了"的成本比重新下 27MB 高，而 27MB 只要几秒。这是刻意选的笨办法。

### 4.4 翻页与删旧（A8 / A9 / A10 的落点）

翻页必须是一个**同步函数**，中间不含任何 `await` / `setTimeout`：

```js
function flip(newDir, items) {       // 同步执行
  player.stop();                     // ① 停 <video>，释放文件句柄
  player.setQueue(items);            // ② 换队列，回到第 1 项
  player.start();                    // ③ 首项立即渲染
  const old = currentDir;
  currentDir = newDir;               // ④ 单槽：直接换指针
  writeIndex({ dir: newDir, items });// ⑤ 落 index.json
  setImmediate(() => purge(old));    // ⑥ 渲染让出去之后再删旧目录
}
```

**① 为什么 `stop()` 必须在最前面**：Windows 上 `<video>` 占着文件时 `rm` 必然失败。
先停播释放句柄、再换指针、最后才删——**顺序错了 A8 永远过不了**，这是实机才会暴露的坑。

**⑥ 为什么 `purge` 要 `setImmediate`**：删 27MB 在主控盘上可能几十毫秒，同步删会卡住下一帧，A2 立刻破。
让它离开当前 tick，画面先翻过去，删除在后台完成。

`purge(old)` 的实现与兜底：

1. `fs.rm(old, { recursive: true, force: true })`
2. 成功 → 日志 `[switch] purged X300 27.1MB`
3. 失败（`EBUSY` / `EPERM`）→ 进 `pendingPurge` 队列：**60 秒后重试 → 启动时重扫 → 连续 3 次失败顶栏告警**
4. 无论成功失败，`index.json` 只保留当前目录（下次启动不会把旧目录当有效内容）

> 这条兜底不是可选项。**没有它，A8 在实机上大概率通不过**——视频文件被解码器占住是必然发生的，
> 而"删不掉就静默跳过"会让磁盘在几周后悄悄堆满旧型号。

**掉队者的自愈（A10 的另一半）**：超时强 activate 时没备完的那台，此刻状态是 `phase=idle, seq=43, modelCode=X400`，
但它盘上还是 X300。它继续下载，下完后**先 flip 再更新 `appliedSeq = 43`**，红字告警自动消失。

**红字要能挡住"开始作业"的冲动**：`内容未就绪 · 请勿作业`，红底白字 + 边框闪烁（CSS 动画实现，不用 JS 定时器）。
工人看到这个，不会误以为自己看的是新型号——这是 A10 存在的全部意义。

### 4.5 为什么用长轮询，不用 WebSocket / SSE

- 长轮询在原生 `http` 上就能写，零依赖；SSE 要处理分块与断流重连；WebSocket 要引 `ws`
- 25 秒挂起 ≈ 一次普通请求，无线抖动时重连成本极低
- 断线后终端 30 秒兜底轮询，网络恢复自动接上，**不需要任何重连状态机**
- 切换是**低频事件**（每天 2–3 次），长轮询的"多一次握手"完全无所谓；反向 WebSocket 常连接在无线车间反而是负担

### 4.6 带宽预算：5 分钟为什么一定够

| 场景 | 需要 | 现实 |
|---|---|---|
| 单台在 5 分钟内下完 27MB | **90KB/s** | 车间任何可用的 WiFi 都远超这个 |
| **5 台并发**（最坏同时切） | 5 × 90KB/s = **450KB/s ≈ 3.6Mbps** | 5GHz 40MHz 单 AP 实测 ≥20Mbps，**5 倍余量** |
| 正常情况（实际吞吐 200Mbps） | 135MB ÷ 25MB/s | **约 6 秒** |

所以双槽预取、错峰限速这些手段全部不需要——**带宽本来就不是瓶颈**，瓶颈原来是"要求 10 秒"这个人为约束。

**真要担心的不是慢，是断**：下载中途掉线会导致重试，反而更久。这是 6.6 里"连续 10 分钟不断流"
比"峰值速率"更该测的原因。真遇到带宽极差（总带宽 <4Mbps），服务端按 `op` 顺序给每台错开 3 秒启动，
避开 AP 队列拥塞，代价是最后一个晚 12 秒开始——仍在 5 分钟内。

## 5. 终端本地存储（决定 A2/A3/A4/A8 能不能过）

### 5.1 目录结构：只有一个 current

```
%LOCALAPPDATA%\online-vwi-terminal\
  config.json    {op, server, kiosk, autoStart}
  content\
    index.json   当前这套内容的索引 {modelCode, modelId, seq, items:[{mediaId,ext,kind,dwellSec}]}
    current\     正在播的那一套，文件名 <mediaId>.<ext>（mediaId 就是 sha256 前 16 位）
  logs\terminal.log
```

- `current\` 就是**唯一在播的那一套**，任何时刻只对应一个（型号 × 工序）
- 目录名**不带型号**：型号改名、中文、特殊字符都不会引发路径问题
- `index.json` 是唯一索引；损坏或与 `current\` 不符 → 按"无内容"处理重拉。**不做自动修复**，因为重下只要几秒
- 磁盘常态占用 **约 27MB**。超过 60MB 就说明有旧文件没删干净——这是 A8 最直观的判据
- `config.json` 优先生效的是 **exe 同级目录**那份（运维批量改它最方便），启动时同步一份到本目录

### 5.2 翻转那一下，文件怎么换（实现修正，与 v0.4.0 不同）

v0.4.0 写的是"目录三步 rename：`current → old_<ts>`，`tmp → current`"。**实机做不出来**，改为
**文件级共存 + 精确删除**。原因是 exe 里停播和换目录分属两个进程：

- 目录 rename 必须等渲染层真的把 `<video>` 关掉才可能成功，而这段等待就是一个**可测量的黑屏窗口**，直接违反 A2
- 跨进程的"停 → 改 → 起"没有原子性可言，中间任何一步失败都会留下一个既不是新也不是旧的目录

现在的做法（`terminal/src/cache.js`）：

```
① 新文件下到 current\，先写 <mediaId>.<ext>.part
② 边下边算 sha256，校验通过才改名成 <mediaId>.<ext>（文件名不同，天然不覆盖旧文件）
③ 新内容在隐藏层预载完成 → 渲染层一次性切换可见层（双缓冲，零黑屏）
④ 渲染层 ack → 主进程写 index.json → 删掉"不在新清单里"的文件
```

三件事因此成立：

| A2 / A4 的底线 | 翻转成功之前，旧文件一个都没动。断电、断网、切换失败都毁不掉正在播的内容 |
|---|---|
| A8 | 翻转后按新清单精确删除，稳态下目录里只有当前一套；连切 3 次文件数不增长 |
| A9 | 渲染层换队列是一次同步调用（`flip`），中间没有 `await`，队列和画面一起变 |

**`.part` 的意义**：正式文件名只代表"完整且校验过的内容"。因此"文件存在"就可以跳过下载，
连点三次切换也不会重复拉同一个文件。启动时把所有 `.part` 直接删掉重下——
判断"哪个下完了"的成本比重新下 27MB 高。

**删不掉怎么办**：Windows 上 `<video>` 或缩略图缓存占住文件时 `EBUSY/EPERM` 是常态。
进 `pendingPurge` 队列 → 60 秒后重试 → 启动时再扫一遍 → 连续失败记日志。
**不做静默跳过**，否则磁盘会在几周后悄悄堆满旧型号。

### 5.3 首次装机与冷启动

新机器第一次开机本地什么都没有，走"自补内容"路径，与切换共用同一套下载代码：

| 时刻 | 动作 |
|---|---|
| 开机 → 长轮询 | 拿到 `idle` + `modelCode`；判断依据是"本地有没有这个型号"，不看 `phase` |
| 本地没有 → 直接下载 | 顶栏 `正在获取内容 3/11`，中间显示等待页 |
| 下完 → flip | 起播 |
| 若此时服务端正在 prepare | 优先下 `pendingModel`，避免"刚下完旧的又被换掉" |

**等待页不能是纯黑**：全新机器黑屏几秒，现场会以为机器坏了。显示型号 + 工序 + 进度条 + "正在获取内容"。

### 5.4 离线兜底

| 场景 | 结果 |
|---|---|
| 断网，`current\` 有内容 | ✅ 照常循环播放，顶栏 `离线`（灰，不打扰）。这就是 A4 的全部实现 |
| 断网，本地无内容（新机器） | 显示等待页 + 每 10 秒重试，画面不闪不跳 |
| 断网时点了切换 | 终端收不到指令（服务器也在同一 AP 后面），网络恢复后自动补。**不测这个场景**，见 A3 口径 |

播放本身在物理上不依赖网络——文件都在 `current\` 里。**网络只影响下载那一段**，这是 6.7 里
"要求从 50Mbps 降到 90KB/s"的根本原因。

### 5.5 服务端媒体回收

媒体是内容寻址的，多个（型号 × 工序）可能引用同一个 sha。所以**服务端不能跟着终端一起删**：

- 终端删自己的 `old_<ts>\`，与服务端完全解耦，互不通知
- 服务端的 `POST /api/media/gc` 只删"`item` 表里零引用"的媒体
- 工程部把某张图从所有清单移除后，该文件**不会自动消失**，需手动点 GC 或等每日定时任务

> 为什么不自动：工程部编辑清单时会有中间态（刚删了又加回来），自动 GC 会误删正在用的文件。
> 手动/定时是安全的，代价是磁盘暂时多占几 MB——可接受。

## 6. 接收端（Electron exe）

### 6.1 进程结构（已实现，`terminal/`）

```
main.js            窗口 / kiosk / 看门狗 / 自启 / 托盘 / 快捷键拦截
 ├─ src/config.js   config.json 读写，路径全 ASCII（%LOCALAPPDATA%\online-vwi-terminal）
 ├─ src/net.js      长轮询、下载（边下边算 sha256）、POST
 ├─ src/cache.js    磁盘内容：.part → 校验 → 正式名；index.json；精确删除 + pendingPurge
 ├─ src/sync.js     同步状态机：长轮询 → prepare 下载 → 举手 → 等 activate → 通知翻转
 ├─ preload.js      只暴露 6 个方法（snapshot / onView / onStatus / flipped / log / 设置页那套）
 └─ renderer/       player.html（播放）+ setup.html（装机向导）
```

**主进程独占网络与磁盘，渲染层只看 file:// 路径。** 两个理由：

- exe 加载的是本地页面，`file://` 去 fetch 服务器是跨源；而且断网时页面若从 http 加载，连界面都起不来，A3/A4 直接不成立
- Node 侧才能边下边算 sha256、才能直接写文件

**窗口约束**：kiosk + 无边框 + 置顶 + `backgroundThrottling:false`（失焦不降频，否则翻页会卡）。
拦截 F11/F12/F5、Ctrl+R/W/N/P/O/U、Ctrl+Shift+I/J/C、Alt+F4；右键菜单与 `will-navigate` 一律禁掉。

**看门狗**：每 10 秒读一次 `window.__vwiBeat`（页面每秒打点），连续 3 次读到「太旧/读不到」就 reload。
`unresponsive` 与 `render-process-gone` 也各自兜一次，避免白屏挂在那里没人知道。

**开机自启**：`app.setLoginItemSettings({openAtLogin})`，开发模式不写（否则注册的是 electron.exe）。

**维护逃生门**：`Ctrl+Alt+Shift+Q` 直接退出。kiosk 下任务栏可能被置顶窗口盖住、托盘点不到，
没有这个组合键就只能拔电源或开任务管理器。托盘菜单另给了「重新同步内容 / 打开内容目录 / 打开日志 / 更改设置」。

**配置优先级**：exe 同级 `config.json` > `%LOCALAPPDATA%` 里的那份。前者存在时会覆盖后者并同步一份过去——
这样"改部署包里的 config.json 再重启"就能换配置，不用进程序点。缺配置不黑屏，弹装机向导（探服务器 → 选工序 → 保存）。

### 6.2 渲染进程（播放器）

- **固定设计稿 1280×1024**，用 `transform: scale()` 适配任意实际分辨率。不做响应式——5:4 屏上响应式必错，缩放最稳。
- 播放单元只有两种：`<img>` 与 `<video>`。预加载下一张图（避免闪白），视频播完即下一项。
- 图片默认停留 **10 秒**（可按项调整），视频播完自动下一项。
- 切型号**不重载页面**，只替换播放队列并回到第 1 项——重载会闪白，违反 A2。
- 单条内容出错（图裂、视频解码失败）跳过并在角落记录，不卡死整个循环。
- **内容不全**（清单项数 < 服务器报告应有数）→ 照播，顶栏挂橙色 `内容不全 8/11`，不静默
- **切换准备中**（prepare 阶段下载中）→ 画面照旧播旧内容，顶栏挂蓝色 `正在切换到 X400 · 3/11`，**绝不切一半**
- **掉队未就绪**（超时强翻但它没备完）→ 顶栏红字 `内容未就绪 · 请勿作业` + 边框闪烁，翻完自动消失
- 翻页是同步函数（见 4.4），渲染层不感知"切换中"这个中间态；中间态只存在于下载准备阶段

### 6.3 界面（1280×1024，三区）

```
┌──────────────────────────────┐  0
│ 顶栏 88px    X300 · OP30   ● │  型号 + 工序 + 在线点
├──────────────────────────────┤  88
│                              │
│      内容区 816px             │  图满宽 / 视频 1280×720 居中，上下留 #1a1a1a
│                              │
├──────────────────────────────┤  904
│ 底栏 120px   2/7 ●●○○○○○     │  进度点 + 页码
└──────────────────────────────┘  1024
```

字号按 1 米观看定：顶栏 **32px**、底栏 **28px**、离线/告警 **36px**。

## 9. 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| 19 寸屏实际是 1366×768 | 中 | 播放器读实际分辨率，设计稿等比缩放；内容规格不变 |
| 无线 5GHz 在屏位置衰减 | 中 | 先现场实测；不足则加 AP 或改有线（5 台，交换机成本很低） |
| Windows 自动更新半夜重启 | 高 | LTSC 或组策略关闭更新；开机自启 + 看门狗兜底 |
| 工程部出图是 16:9 手机截图 | 高 | 上传时检测宽高比，非 5:4 / 4:3 弹提醒并给裁剪建议 |
| 以后需要"某道工序单独跑别的型号" | 中 | 一期明确不做。真出现时把 `setting` 换成"工序 → 型号"的映射表，改动约半天 |
| **旧文件被 `<video>` 占住删不掉，磁盘悄悄堆积** | **高** | `pendingPurge` + 60 秒重试 + 启动重扫 + 连续 3 次失败顶栏告警；A8 用"连续切 3 次看目录是否增长"来验 |
| 5 台同时下载把 AP 队列打满，切换拖到 5 分钟外 | 低 | 5 台只需 3.6Mbps，正常 AP 有 5 倍余量；真不够则按 `op` 错峰 3 秒启动 |
| 班长误操作连点切换，终端反复取消重下 | 中 | 无功能损失（最终收敛到最后一次），只是多耗几秒流量；管理端二次确认弹窗挡住手滑 |
| 掉队终端一直亮红字没人管 | 中 | 管理端把"未就绪"的工序列成清单，切换完成后仍挂着，直到该屏补完 |
