> ② 终端缓存由"全量预下发 10 型号"改为**双槽 A/B**（当前 + 预备），本地常驻 2 套 ≈ 54MB，

>
> **v0.2.0 修订**（破坏性变更：取消工位实体）：数据表 6 → **5 张**（删 `station`，新增 `setting`）；
> 接口重排为 **12 个**（删 3 个工位接口，加 `/api/processes`）；终端不再有令牌，身份 = 工序代码 `op`；
> 换型由"逐台改型号"改为"改一个全局值 + 唤醒长轮询"。

## 0. 一页结论

| 项 | 决定 |
|---|---|
| 服务器 | 一台 Windows 电脑，Node 22 + **内置 SQLite**，零 npm 依赖 |
| 接收端 | Electron exe，1280×1024 设计稿 + 缩放，kiosk 全屏 + 开机自启 + 看门狗 |
| 层级 | **型号 → 工序 → 清单**，到此为止，无工位 |
| 终端身份 | 启动参数 `?op=OP30`，只此一个值，不注册不建档案 |
| 切换通道 | **长轮询**（挂 25 秒）+ 30 秒兜底，不用 WebSocket/SSE |
| 内容存储 | `media/<sha256前16>.<ext>` 内容寻址，天然去重 |
| 切换语义 | **整批原子切换**：一次 `seq` 跳变，5 台同帧翻，先备齐后翻 |
| 终端缓存 | **双槽 A/B**，常驻当前 + 预备 2 套 ≈ **54MB**，切完即删旧槽 |
| 切换耗时 | 预备命中 **<1 秒**；未命中现场拉 27MB 约 5 秒（仍过 A1 的 10 秒） |
| 数据表 | **5 张** |
| 接口 | **12 个** |

一句话：**服务器存内容、记一个"现在做哪个型号"、把这个值一次广播出去；终端本地只压着 2 套内容（当前 + 预备），切换是整槽对调整槽，翻过去就把旧槽删掉。**

## 2. 数据模型（5 张表）

```sql
-- 产品型号
model   (id, code UNIQUE, name, enabled, sort)

-- 工序：5 条固定记录，也是终端唯一的身份
process (id, code UNIQUE, name, sort)

-- 媒体：内容寻址，同一文件只存一份
media   (id PK = sha256 前 16 位, sha256, kind 'image'|'video',
         ext, bytes, width, height, duration_ms, created_at)

-- 播放清单项：(型号 × 工序) 下的一条
item    (id, model_id, process_id, ord, kind, media_id,
         dwell_sec, UNIQUE(model_id, process_id, media_id))

-- 全局状态：KV，三把钥匙
setting (key PK, value)        -- current_model_id / prefetch_model_id / seq
```

**为什么 `setting` 就够**：换型是全网统一的，服务端只需记住"现在做哪个型号"这一个值，
外加一个"下一个该备哪个型号"（`prefetch_model_id`）——这是"整批原子切换"能在 1 秒内发生的唯一前提。
没有工位，就不存在"每台各自型号"，也就不需要 `station` 表和任何逐台状态。

**`prefetch_model_id` 怎么定**：默认取"启用型号里按最近使用时间排序的下一个"，
班长也可以在管理端点名"下次切 X400"直接改这个值。它是**建议**不是约束——终端备错了只是慢 5 秒，不会切错。

**刻意不建的表**：`station`（已取消）、`user` / `session`（不做权限）、`release`（不做版本治理）、`play_log`（不做统计报表）、`page` / `block`（不做版式）、`switch_log`（切换记录写进程日志即可）。

## 3. 接口（12 个）

| # | 方法 | 路径 | 说明 |
|---|---|---|---|
| 1 | GET | `/api/models` | 型号列表，带**内容完成度**（50 套里齐了几套） |
| 2 | POST / PUT | `/api/models[/:id]` | 新建 / 改名 / 停用 |
| 3 | GET | `/api/processes` | 5 道工序 |
| 4 | GET | `/api/playlist?modelId=&processId=` | 管理端取某型号某工序的清单 |
| 5 | PUT | `/api/playlist` | **整批保存**（一次提交该工序全部项，避免逐条增删的中间态） |
| 6 | POST | `/api/media/upload?filename=&kind=` | 流式上传，返回 sha 与宽高 |
| 7 | GET | `/api/media` | 媒体库（带被引用次数） |
| 8 | POST | `/api/media/gc` | 清理无引用媒体 |
| 9 | POST | `/api/switch` | **核心**：`{modelCode, prefetch?}` 全线整批切换 |
| 10 | GET | `/api/state?since=<seq>` | **长轮询**：返回 `{seq, modelCode, prefetch, online[]}` |
| 11 | GET | `/display/playlist?op=OP30&model=X300` | 拉**指定型号**本工序的清单与媒体地址（当前槽刷新与预备槽下载共用此接口） |
| 12 | GET | `/m/:id` | 媒体文件，支持 Range |

管理界面本身是静态文件，不占接口。

**终端不鉴权**：只带 `op` 参数，没有令牌。因为一期没有权限体系、只部署在内网，工序代码也不是秘密。
代价是内网任何人能拉到内容——可接受，但**服务器绝不能直接暴露到办公网或外网**。

## 4. 切换协议（决定 A1 / A9 能不能过）

### 4.1 服务端：一次事务，一次广播

全局维护 `seq`（存 `setting`）。`POST /api/switch {modelCode, prefetch?}` 在一个事务里做三件事：

```sql
BEGIN;
  UPDATE setting SET value = :newModelId  WHERE key = 'current_model_id';
  UPDATE setting SET value = :nextModelId WHERE key = 'prefetch_model_id';  -- 可缺省，缺省则按 LRU 推算
  UPDATE setting SET value = CAST(value AS INTEGER) + 1 WHERE key = 'seq';
COMMIT;
-- 提交成功之后，才唤醒挂起的请求（内存事件发射器）
```

**顺序不能反**：必须先落库再唤醒。否则终端被唤醒后回查状态时可能读到旧值，出现"唤醒了但型号没变"的抖动。

`GET /api/state?since=N`：
- `seq > N` → 立即返回 `{seq, modelCode, prefetch, online}`
- 否则挂起，最多 25 秒；超时返回当前值（让终端确认链路活着，同时兼作心跳）

`online` 字段来自内存 `Map<op, lastSeenAt>`，随每次 `/api/state` 与 `/display/playlist` 请求刷新，**不落库**，服务重启后 30 秒内自动重建。

**为什么这样就是"一起切"**：5 台终端挂的是同一条长轮询，服务端在唤醒时遍历挂起表逐个 `resolve`——
这个过程在同一个事件循环 tick 里完成，彼此间隔是**微秒级**，不是"排队下发"。网络再差也是 5 个 HTTP 响应同时飞出去。

### 4.2 终端：只认最新状态，不做命令队列

终端只保存一个数：`appliedSeq`（已经生效的 seq）。

```
loop:
  r = GET /api/state?since=appliedSeq        (25 秒超时)
  if r.seq <= appliedSeq: 继续 loop           -- 超时心跳，状态没变

  target = r.modelCode
  if target == 当前槽.modelCode:
      appliedSeq = r.seq; 继续 loop          -- 已经是这个型号（比如自己重启前就切过了）
  else:
      进入就绪检查（见 4.3）
```

**关键设计：状态机而不是消息队列。** `seq` 表达的是"现在应该是什么型号"，不是"请执行第 N 号命令"。
所以班长连点三次 X300→X400→X300，终端只会朝最后一个状态收敛，中间态被自然跳过——
**不可能出现"翻到 X400 停了 200ms 再翻回 X300"的闪动**，这是 A9 的保证机制。

### 4.3 就绪检查与"先备齐后翻"

收到目标型号后，终端按顺序做：

| 步骤 | 判断 | 动作 |
|---|---|---|
| 1 | 预备槽的 `modelCode` == 目标 且清单项数 > 0 | 是 → 跳到 3 |
| 2 | 否则现场下载该（目标 × 本工序）的清单与全部媒体文件 | 边下边更新顶栏 `准备中 3/11`；**画面继续播旧内容，不闪不黑** |
| 3 | 逐文件校验 sha256（只校验本次新下载的，已备好的跳过） | 失败 → 删掉该文件重下一次，仍失败 → 该项标记缺失，继续 |
| 4 | 全部就绪（或仅剩"缺失"项） | 执行**翻槽** |

**翻槽这一步必须是原子操作**，代码上是一个函数，不含任何 `await`：

```js
function flip(newSlot) {          // 同步执行，中间不 await、不 setTimeout
  player.stop();                  // 停当前 <video>，释放句柄
  player.setQueue(newSlot.items); // 换队列，回到第 1 项
  player.start();                 // 首项立即渲染
  [currentSlot, backupSlot] = [newSlot, currentSlot];
  currentSlot.activate();
  backupSlot.purge();             // 旧槽文件删除（见 4.4）
}
```

**为什么强调"不含 await"**：翻槽中间只要有一个异步点，就会出现"队列已换、画面还是旧的"或反之，
工人看到一屏里一半新一半旧。把整个切换压成一次同步调用，是这件事在代码层面唯一可靠的做法。

### 4.4 旧槽清理（A8 的落点）

`backupSlot.purge()` 在翻槽后**立即同步调用**，不等定时任务、不等下次启动：

1. 删 `slots/<旧modelCode>/` 整个目录（`fs.rmSync(recursive)`）
2. 更新本地 `index.json`：只保留当前槽条目
3. 写一行日志 `[switch] purged <modelCode> 27.1MB`

**删不掉的兜底**：Windows 上文件被 `<video>` 或缩略图缓存占住时 `EBUSY/EPERM` 是常态。
所以 `purge` 失败不抛错，而是把该目录加入 `pendingPurge` 列表：
- 翻槽后 60 秒重试一次
- 下次启动时再扫一遍
- 连续 3 次失败 → 记日志并顶栏显示告警（说明有文件句柄泄漏，需要排查）

> 这条兜底不是可选项。**没有它，A8 在实机上大概率通不过**——视频文件被解码器占住是必然发生的，
> 而"删不掉就静默跳过"会让磁盘在几周后悄悄堆满旧型号。

### 4.5 为什么用长轮询，不用 WebSocket / SSE

- 长轮询在原生 `http` 上就能写，零依赖；SSE 要处理分块与断流重连；WebSocket 要引 `ws`
- 25 秒挂起 ≈ 一次普通请求，无线抖动时重连成本极低
- 断线后终端 30 秒兜底轮询，网络恢复自动接上，**不需要任何重连状态机**
- 切换是**低频事件**（每天 2–3 次），长轮询的"多一次握手"完全无所谓；反向 WebSocket 常连接在无线车间反而是负担

### 4.6 为什么切换不发内容

切换只传 `modelCode`（几十字节），内容靠预备槽提前备好。这是 A1「10 秒内」的物理基础——不是优化技巧，是设计前提。
反过来，如果切换时才发内容，5 台并发下载 27MB×5=135MB，50Mbps 共享带宽下要 20 秒以上，**A1 直接不成立**。

## 5. 下发与缓存（决定 A2/A3/A4/A8 能不能过）

### 5.1 双槽目录结构

终端本地只有两个槽，命名不跟型号走，避免"型号改名"引发路径问题：

```
%LOCALAPPDATA%\online-vwi\
  index.json          {slotA:{modelCode,seq,ready}, slotB:{...}, current:"A", appliedSeq:42}
  slots\
    A\                playlist.json  +  媒体文件（<mediaId>.<ext>）
    B\                playlist.json  +  媒体文件
  logs\switch.log
```

- `index.json` 是**唯一索引**，启动时只信它；它损坏或与目录不符 → 按"无缓存"处理，重新拉当前型号
- 槽内容是**自包含**的：`playlist.json` 里存的是媒体 id 与本地相对路径，脱离服务器也能播
- 磁盘占用常态 54MB 左右。**任何时刻都不会出现第三个槽的目录**——这是 A8 的判据之一

### 5.2 预取（谁去备"下一个型号"）

| 时机 | 动作 | 限流 |
|---|---|---|
| 启动后 30 秒 | 拉当前型号清单，校验本地文件，缺失的补 | 3 并发 |
| 当前槽就绪后 | 读 `/api/state` 的 `prefetch`，把该（型号 × 本工序）下载到空闲槽 | **单文件串行**，每完成一个歇 200ms |
| 每次 `/api/state` 心跳 | 若 `prefetch` 变了 → 取消旧下载任务，改备新的 | — |
| 翻槽后 | 新空闲槽立刻开始备"再下一个" | 同上 |

**限流为什么是"单文件串行"**：5 台终端同时全速拉，会把 5GHz AP 的队列打满，导致正在播的视频卡顿——
**预取绝不能影响播放**。宁可备得慢一点（27MB 串行约 6 秒），也不要在生产时段抢带宽。

预取优先级：`prefetch` 指定的型号 > 上次切走的那一个（支持"切回去"的场景）> 无。

### 5.3 离线兜底（口径变了，必须说清）

终端本地 `index.json` + `slots/` 自包含，网络全断时：**照当前槽继续循环播放，顶栏显示"离线"**。

但"本地只留 2 套"带来一个必须承认的限制：

| 场景 | 结果 |
|---|---|
| 断网 + 切到**预备槽里的型号** | ✅ 正常切，0 秒（A3 就是测这个） |
| 断网 + 切到**第三个月份没备的型号** | ❌ 切不了。顶栏显示 `X500 未下载 · 等待网络`，画面继续播旧内容，网络恢复后自动补下再翻 |
| 断网 8 小时 | ✅ 不中断（A4），因为播放只依赖本地文件，与网络无关 |

> 这是"旧文件不保留"的**直接代价**，写在这里而不是藏着：本地只留 2 套，就没有"断网还能切任意型号"这回事。
> 换来的是终端磁盘从 1.4GB 降到 54MB、旧内容不留、A8 可验证。
> 评估过现场：一天 2–3 次换型、网络故障是偶发，**班长在换型前本来就知道要切哪个型号**（`prefetch` 就是为此设的），
> 所以这个限制在一期不会真正咬人。若日后车间出现"无预警临时换型 + 网络差"，再把预备槽扩到 3 个即可，不动协议。

### 5.4 文件校验

下载完成后算 sha256 与文件名比对，不一致则删除重下（最多 2 次）。**不做**清单签名（内网、无攻击面诉求）。

播放时**不再校验**（每次起播都算一遍 sha 会让切换变慢），只在下载落盘时校验一次——这是性能与可靠的折中点。

### 5.5 服务端媒体回收

媒体是内容寻址的，多个（型号 × 工序）可能引用同一个 sha。所以**服务端不能跟着终端一起删**：

- 终端删自己的槽，与服务端完全解耦，互不通知
- 服务端的 `POST /api/media/gc` 只删"`item` 表里零引用"的媒体
- 工程部把某张图从所有清单里移除后，该文件**不会自动消失**，需要手动点一次 GC 或等每日定时任务

> 为什么不自动：工程部正在编辑一套清单时会有中间态（刚删了又加回来），自动 GC 会误删正在用的文件。
> 手动/定时是安全的选择，代价是磁盘暂时多占几 MB——可接受。

## 6. 接收端（Electron exe）

### 6.1 进程结构

```
main.js
 ├─ 读配置（op=OP30、server=http://192.168.x.x:8092）
 ├─ 创建 BrowserWindow（kiosk、无边框、置顶、禁用右键/DevTools/F11/Alt+F4）
 ├─ 开机自启（HKCU\...\Run 或 shell:startup 快捷方式）
 ├─ 看门狗：每 10 秒向渲染进程要心跳，连续 3 次无响应 → reload
 ├─ 断网检测：请求失败计数 + net 模块
 └─ 托盘图标（维护用，工人看不见）
```

终端不需要配置向导：**一个 `config.json` 里两行**（`op` 与 `server`），装机时填好即可。

### 6.2 渲染进程（播放器）

- **固定设计稿 1280×1024**，用 `transform: scale()` 适配任意实际分辨率。不做响应式——5:4 屏上响应式必错，缩放最稳。
- 播放单元只有两种：`<img>` 与 `<video>`。预加载下一张图（避免闪白），视频播完即下一项。
- 图片默认停留 **10 秒**（可按项调整），视频播完自动下一项。
- 切型号**不重载页面**，只替换播放队列并回到第 1 项——重载会闪白，违反 A2。
- 单条内容出错（图裂、视频解码失败）跳过并在角落记录，不卡死整个循环。
- **内容不全**（清单项数 < 服务器报告应有数）→ 照播，顶栏挂橙色 `内容不全 8/11`，不静默
- **切换准备中**（目标未备好）→ 画面照旧播旧内容，顶栏挂蓝色 `正在切换到 X400 · 3/11`，**绝不切一半**
- 翻槽是同步函数（见 4.3），渲染层不感知"切换中"这个中间态；中间态只存在于准备阶段

## 9. 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| 19 寸屏实际是 1366×768 | 中 | 播放器读实际分辨率，设计稿等比缩放；内容规格不变 |
| 无线 5GHz 在屏位置衰减 | 中 | 先现场实测；不足则加 AP 或改有线（5 台，交换机成本很低） |
| Windows 自动更新半夜重启 | 高 | LTSC 或组策略关闭更新；开机自启 + 看门狗兜底 |
| 工程部出图是 16:9 手机截图 | 高 | 上传时检测宽高比，非 5:4 / 4:3 弹提醒并给裁剪建议 |
| 以后需要"某道工序单独跑别的型号" | 中 | 一期明确不做。真出现时把 `setting` 换成"工序 → 型号"的映射表，改动约半天 |
| **旧槽文件被 `<video>` 占住删不掉，磁盘悄悄堆积** | **高** | `pendingPurge` 列表 + 60 秒重试 + 启动重扫 + 连续 3 次失败顶栏告警；A8 用"连续切 3 次看目录是否增长"来验 |
| 预备型号猜错，每次换型都要现场等 5 秒 | 中 | 班长在管理端点名"下次切谁"；仍频繁则把槽数从 2 扩到 3（代码只改预取策略一处） |
| 断网 + 切到未备型号，切不动 | 中 | 顶栏明示 `未下载 · 等待网络`，画面继续播旧内容；网络恢复自动补下再翻。不静默失败 |
