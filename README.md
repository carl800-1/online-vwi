# ESOP 发布系统

产线**可视化作业指导书（VWI）**的在线发布与换型系统。

一台 PC 作服务器，每道工序一块屏。工程部在服务器上按「机种 × 线体 × 工位」配好播放清单，
**班长在总览页选机种、点换型，全线屏同时换成新机种的指导书**——不用换纸、不用换 U 盘、不用挨个工位跑。

> 独立自研项目。不基于任何第三方产品的代码，内容模型与切换协议均为本项目设计。

---

## 一、内容模型：机种 × 线体 × 工位

```
线体 一线 (启用中) ─┬── OP10 ─┐
                    ├── OP20 ─┤   只是"这条线有几块屏"
                    └── OP40 ─┘
                                 ↓ 工位按这条线的工序长出来
机种 X200 @ 一线 ─┬── OP10 工位 ── 播放清单（图 / 视频 / PDF 页，有序，循环播）
                  ├── OP20 工位 ── 播放清单
                  └── OP40 工位 ── 播放清单

线体 二线 (未启用) ─┬── OP10 ─┐
                    └── OP30 ─┘       ← 工序都不一样
机种 X200 @ 二线 ─┬── OP10 工位 ── 另一套内容
                  └── OP30 工位 ── 另一套内容
```

三层各管一件事：

| 层 | 管什么 | 数据表 |
|---|---|---|
| 线体 | 这条线**有几块屏**、编号是 OP10/OP20/… | `line` / `process` |
| 工位 | **这个机种在这条线上**的这块屏播什么 | `station` / `station_req` / `item` |
| 机种 | 产品本身（编码、名称） | `model` |

**内容按「机种 × 线体」各存一份。** 为什么不是全厂一份？因为同一个机种在一线和二线
的工艺路线可以完全不同 —— 工序数量不同，甚至同一串 OP 号含义都不一样
（一线 OP30 是压装、二线 OP30 是检测）。靠工序码跨线对位一定会让二线的屏播出
二线根本不该看的 SOP。

两条线大体相同时不必重录：**「从其它线复制…」**把另一条线整套工位（允许类型 + 文件 + 顺序）
搬过来，再改不一样的那一两处。复制出来是完全独立的两份，改一边不影响另一边。

**仍然没有工位档案、没有终端注册、没有逐台设置**——"工位"只是机种里的一个内容槽位，不是一台设备。

带来三个直接后果：

| 后果 | 原因 |
|---|---|
| 换型是**单线统一**的 | 每条线体只有一个"现在做哪个机种"，一条线换型不影响另一条 |
| 内容**按线各一份** | 两条线工艺不同就互不干扰；相同就复制一份再改 |
| 删线**连内容一起删** | 工位是这条线专属的，线没了它没人读，留着只会变成看不见的孤儿数据 |

---

### 工位要求：规定"这个工位允许放什么"

```
机种 X200 @ 一线          ← 先选机种，再选线体
  └ 工位 OP30
      ├ 允许类型 ── 图片 / 视频 / PDF（有行 = 允许，min_count = 至少几份）
      ├ 单文件体积上限
      └ 内容清单 ── 按顺序播，可设停留秒数
```

- 某个 kind **有行** → 允许放这类文件，`min_count` 是"至少几份"
- 某个 kind **没行** → 这个工位不接受这类文件，上传直接被服务端拒（`400 这个工位不允许放视频：…`）
- reqs **整张为空** → 视为未配置，**不做类型锁**（迁移后不必先勾一遍才能用）

保存是**整批覆盖**：内容与要求一次 `PUT` 提交，前端先整批校验，后端事务内先删后插，不留半套。

## 二、换型机制（本项目最关键的部分）

### 两段式：先备齐，再一起翻

工位屏网速不一样。如果各下各的、下完各自翻，快的 3 秒翻、慢的 40 秒翻，
中间这半分钟里前道已按新型号作业、后道还看着旧型号 —— **直接混批**。

所以切换分成两段：

```
① 班长点"切换到 X400"
   └─ 服务器 phase=prepare，广播目标型号（此时画面不动，继续播旧内容）
   └─ 各终端后台下载并校验本工序内容，顶栏显示"准备中 3/11"
   └─ 下完 → POST /api/ready 举手
② 所有在线终端都举手
   └─ 服务器 phase=activate，seq+1
   └─ 各终端同一瞬间整屏翻，翻完立即释放旧内容
```

**铁律：要么整批全翻，要么一台都不翻。** 不存在"一屏里混两个型号"的中间态。

### 5 分钟到点也翻

一台屏网络烂不能拖整个产线停产，所以超时（默认 5 分钟）**强制激活**：
备好的翻，没备好的保持旧画面并顶栏红字 `内容未就绪 · 请勿作业`，
管理端能指出是哪道工序没跟上（验收项 A10）。

### 本地只留一套，旧内容切完即删

终端磁盘上任何时候只有**当前这一套**（约 27MB），翻页成功后旧内容立即释放。
不做历史型号归档、不做"回滚到上一型号"的本地快照。好处是终端永远不会拿错型号播。

### 为什么不用 WebSocket

长轮询在原生 `http` 上就能写，零依赖。25 秒挂起 ≈ 一次普通请求，无线抖动时重连成本极低；
断线后 30 秒兜底轮询，网络恢复自动接上，不需要任何重连状态机。

## 三、快速开始

要求 **Node.js ≥ 22.5**（用内置 `node:sqlite`，**零 npm 依赖**，不用 `npm install`）。

```bash
node server.js                  # 默认 8092 端口
node server.js --port=8092      # 指定端口
```

首次启动自动建库并写入种子数据：**10 个机种（X200–X290）**，每个机种自动补齐
**5 个工位（OP10–OP50）**，内容全空。数据落在 `data/`（已 gitignore，含 `vwi.db` 与媒体文件）。

启动后控制台会打印局域网地址，终端装机时直接填：

```
  管理端    http://127.0.0.1:8092/
  终端画面  http://127.0.0.1:8092/player.html?op=OP30
  局域网访问（终端装机器上填这个）：
    http://192.168.1.4:8092
```

### 管理端四块

| 页面 | 干什么 |
|---|---|
| **作业内容**（总览） | 一眼看几条线、各做什么机种、哪几块屏切完了；就地换型 |
| 线体设置 | 建线、启停线、维护每条的工序清单（几块屏、叫什么） |
| 机种设置 | 先选机种、再选线体；**左「工位索引」右「当前工位」**，在这里传 PDF / 图片 / 视频、勾允许类型 |
| 媒体库 / 终端监控 / 系统 | 查文件与清理未引用、看各屏状态、版本与地址 |

> 「作业内容」是**总览**，其余各功能项都是**设置**页——这条分工是有意的：
> 日常只开总览，配置改在设置里，避免误改。

### 工作台上的屏（终端 exe）

浏览器页只用于调试。**真正装在工位屏上的是 `terminal/` 里的接收端程序**：
kiosk 全屏、开机自启、看门狗、内容存在本机 —— 断网继续播，断电重启自己回来。

```bash
cd terminal
npm install        # 首次装 Electron 31（约 260MB）
npm start          # kiosk 全屏；npm run dev 为调试模式
```

装机是 `server`（服务器地址）+ `line`（哪条线体，可留空跟随服务端当前启用线体）+ `op`（哪道工序），
写在 `config.json` 里放 exe 旁边。
另有一个必读点：**维护退出键是 `Ctrl+Alt+Shift+Q`**，kiosk 下任务栏可能被盖住、托盘点不到。

完整说明见 [`terminal/README.md`](terminal/README.md)。

### 服务端（桌面程序，双击即用）

**现场用这个**：`server-gui/dist/ESOP-Server.exe`（v1.9.0），单文件免安装。
双击它就同时干两件事：把 HTTP 服务跑起来、把管理界面开成一个独立窗口——**全程不用浏览器、不用装 Node**。

| 场景 | 做法 |
|---|---|
| 日常使用 | 双击 exe，等窗口出来即可 |
| 关窗口 | **服务不会停**，缩到右下角托盘继续为 5 台终端服务；双击托盘图标能重新打开 |
| 真退出 | 右键托盘图标 →「退出服务端」（有终端在线时会二次确认） |
| 开机自启 | 系统面板里打开开关，或托盘菜单勾选 |
| 终端装机地址 | 系统面板里直接列出局域网地址并可复制，不用去翻 ipconfig |

界面顶栏的「系统」按钮里能看到：版本、服务端口、终端要填的服务端地址、数据目录、日志文件。
数据在 exe 同级的 `data\`，备份就备份它；日志在 `data\server.log`，出问题先看它。

<details>
<summary>源码方式运行</summary>

```bash
npm start            # 等价于 node server.js，监听 8092
npm run gui          # 以桌面程序方式启动（开发调试）
npm run gui:dist     # 打包 portable exe
```

打包环境两个坑（本机内网必需）：

1. **必须走公司代理**：`export https_proxy=http://sha1.sme.zscaler.net:443`。
   不设会报 `unable to get local issuer certificate`。
2. `build.electronDownload.isVerifyChecksum = false` 是**故意开着**的。
   `@electron/get` 每次打包都要联网拉 `SHASUMS256.txt` 校验 electron 的 zip，
   而这个校验文件**不走本地缓存**，代理经常在建连阶段就断（
   `Client network socket disconnected before secure TLS connection was established`），
   表现为每次打包都卡在 `packaging ... win-unpacked` 之后失败。
   electron 的 zip 本身是从 `%LOCALAPPDATA%\electron\Cache` 读的（命中缓存打印 `using cached artifact`），
   跳过的是它的哈希校验。**换机器或首次装依赖后要联网跑一次成功打包**，
   让 zip 进缓存，之后就能离线出包。

</details>

### 日常操作

1. **配内容**：机种设置 → 左边选机种 → **顶部选线体** → 左「工位索引」点一个工序（或按「下一个」顺序过）→ 勾「允许类型」→ 拖入图片 / 视频 / PDF → 排序、设停留秒数 → 保存
2. **换型**：作业内容（总览）→ 在线体卡片里选机种 → 点「换型」→ 等各屏举手 → 全线同时翻
3. **改工序名**：线体设置 → 工序表里点名称，改完会显示在终端顶栏
4. **加/减屏**：线体设置 → 工序表增删（「批量加工序」可一次贴十几二十行）。**加工序后各机种会自动多出对应空工位**，去机种设置传内容即可
5. **换线做同一机种**：机种设置 → 选机种 → 选到新线体 → 「从其它线复制…」选来源线 → 再改不一样的那几道
   （复制只看"目标工位有没有内容"：空着就直接填，已有内容默认跳过，勾 overwrite 才覆盖）

## 四、接口

```
GET    /api/board                 总览：全部线体 + 每线客户端状态 + 有无内容（一次拿完）
POST   /api/board/switch          总览页换型，回 {ok, activated, phase}

GET    /api/models?lineId=         机种列表（stDone/stTotal = 该线体上的工位数）
POST   /api/models                新增机种
PUT    /api/models/:id            改机种（编码 / 名称 / 停用）

GET    /api/stations?modelId=&lineId=  某机种在某条线上的工位（含允许类型与内容）
POST   /api/stations              加工位（body 带 modelId + lineId）
PUT    /api/stations/:id          整批覆盖保存（要求 + 内容；校验失败一条不动）
DELETE /api/stations/:id          删工位（有内容会拒绝）
POST   /api/stations/sync         按本线工序补齐该机种的工位（缺的补，多的不删）
POST   /api/stations/copy         从另一条线整套复制（{modelId, fromLineId, toLineId, overwrite?}）

GET    /api/lines                 线体列表
POST   /api/lines                 新建线体
PUT    /api/lines/:id             改线体 / 启用停用（同时只允许一条启用）
DELETE /api/lines/:id             删线体（连同这条线的工位与内容一起删）
GET    /api/processes?lineId=     某线体的工序清单
POST   /api/processes             加工序
PUT    /api/processes/:id         改工序名
DELETE /api/processes/:id         删工序

GET    /api/playlist?modelId=&processId=    兼容接口：按工序定位到「该线 × 该码」的工位
PUT    /api/playlist              兼容接口：整批覆盖保存
GET    /api/playlist/all          全机种内容一览

POST   /api/media/upload?filename=           原始流上传，自动 sha256 去重
GET    /api/media                 媒体列表（含被引用次数）
POST   /api/media/gc              回收未引用媒体（默认 dryRun）
GET    /api/media/advice          规格体检（非 5:4、图片过大）

POST   /api/switch                {modelCode} 发起换型
POST   /api/switch/cancel         放弃本次换型（画面保持原机种）
POST   /api/ready                 {line,op,modelId} 终端举手：本工序已备齐
GET    /api/state?line=&op=&since=  长轮询（25 秒），返回 phase/seq/current/pending/online/ready

GET    /display/boot?line=&op=       终端启动自检：我是谁、现在该播什么
GET    /display/playlist?line=&op=&model=  终端拉清单（当前槽刷新与预备下载共用）
GET    /m/:id                     媒体流，支持 Range（视频拖动、断点续传）
```

**终端接口契约没变**：`/display/boot` 与 `/display/playlist` 仍按 `?line=&op=` 取，
服务端内部用「线体 + 工序码」定位工位（`stationOf(modelId, line.id, process.code)`），
只多回了 `stationCode` / `stationName` / `noStation` 三个描述字段。
**现场 5 台终端不用改配置、不用升终端。**

**一期无鉴权**（用户明确「先不考虑权限管理」）。`op` 不是权限，而是"我是哪道工序"这个身份。
代价是内网任何人都能拉到内容，所以有一条硬约束：**服务端只能跑在车间内网，不得映射到公网。**

## 五、数据表（7 张）

| 表 | 作用 |
|---|---|
| `line` | 线体（同一时刻只有一条 `enabled=1`） |
| `line_state` | 每条线的换型状态：当前机种、seq、pending、deadline |
| `model` | 机种 |
| `process` | 线体工序（这条线有几块屏，`UNIQUE(line_id, code)`） |
| `station` | 机种 × 线体 × 工位（这块屏播什么，`UNIQUE(model_id, line_id, code)`） |
| `station_req` | 工位允许的文件类型与最小数量、体积上限 |
| `item` | 播放清单项：`(model_id, station_id)` 下的一条，带排序与停留时长 |
| `media` | 媒体，sha256 内容寻址，多机种共用同一张图只存一份 |
| `setting` | 全局 KV：`rev` 等 |

**刻意不建**：`user` / `session`（不做权限）、`release`（不做版本治理）、
`play_log`（不做统计报表）、`page` / `block`（不做版式）、`switch_log`（切换写进程日志即可）。

两个计数器分工要分清：
- `seq` —— 业务语义，**只在激活时 +1**，终端据此判断"该翻页了"（按线体各一份）
- `rev` —— 通信语义，任何需要通知终端的变化都 +1（进 prepare、激活、清单被改），**全局单调**

## 七、测试

```bash
node test/run.mjs                 # 服务端：110 项协议断言（临时实例，跑完焚毁）
cd terminal && node test/sync-test.cjs   # 终端：19 项数据层断言（连真实服务器）
```

服务端测试会起一个**临时数据目录**的实例（默认端口 8093），跑完自动关掉并删除数据——不会弄乱开发数据。

覆盖 110 项断言，重点在切换协议与工位模型：

| 组 | 验的是什么 |
|---|---|
| 档案 | 10 机种 × 5 工序，完成度分母 50（按线体各算各的） |
| 上传清单 | 同文件去重、宽高解析、重复项拒绝、**失败保存不破坏原清单** |
| 无终端在线 | 直接激活（否则管理端永远卡在"准备中"） |
| 两段式 | prepare 不动 seq、1/2 台备好**不激活**、集齐才翻、seq 只 +1 |
| 工序隔离 | 不同工位内容互不影响、空内容显式返回 `empty` |
| **工位带线体** | 每条线的工位是独立记录；一线 OP30 改了，二线 OP30 不动 |
| **工位类型闸门** | 没勾视频 → 放视频 `400`；勾上后放行 |
| **跨线独立** | 同机种换一条线取不到内容（不会借用），除非显式复制 |
| **跨线复制** | 空工位直接填、已有内容跳过、复制后两边独立、再复制不叠加 |
| **工序差异** | 两条线工序数量/编码不同也各长各的工位；加工序自动补；sync 能补回缺的 |
| 过期举手 | 拿旧机种举手返回 409 |
| 放弃切换 | 回到 idle、当前机种不变、不消耗 seq |
| 工位增删 | 有内容的工位不许删；同线工位码唯一；删线体连它的工位一起删 |
| **总览接口** | 一次返回全部线体、每道工序都占一个客户端位、带 `status` 与 `hasContent` |
| 媒体流 | MIME、Range 206、404 |

终端那 19 项测的是真机上最容易翻车的几件事（不需要 Electron，用假渲染层 + 真实文件操作）：

| 组 | 验的是什么 |
|---|---|
| 首次装载 | 内容真的落盘、文件数 = 清单条数、无 `.part` 残留 |
| 切换（A8） | 旧机种独有文件被删、磁盘只剩当前一套 |
| 断电重启（A5） | 不连服务器也能在 110ms 内出画面 |
| 断网（A3/A4） | 画面照样播，状态转离线，不抛错 |
| 连切三次 | 文件数与占用不增长 |

另外 `terminal/test/preview.html?s=1..7` 用假数据源驱动真正的播放器代码，
可逐个核对七种画面状态（需要 `node test/serve.cjs` 起预览服务）。

### 已验证的事实（不是推测）

**服务端（浏览器实测）**
- 两台终端同时在线时，切换 `prepare → both ready → activate` 在 2 秒内完成
- 终端画面从 `X200` 整屏换成 `X210`，顶栏、内容、计数同步变化
- 内容为空时显示橙色 `内容不全 0 项` + 说明，**不静默播空白**
- 播放中修改清单，终端自动重下并翻页（`rev` 通知 + 清单指纹比对）
- 老开发库自动迁移：41 条内容从「线体工序」搬到「机种 × 线体 × 工位」，**按原工序所属线体精确归位**，
  两线补全后共 100 个工位（一线 50 个带 41 条内容、二线 50 个空位），零孤儿、零跨模型错挂
- 机种设置切到一线改 OP30 不影响二线 OP30；复制到二线后两边内容各自独立
- 给二线加 `OP60` 工序后，二线机种自动长出第 6 个工位，一线仍是 5 个；
  终端 `?line=L2&op=OP60` 取到 0 项、`?line=L1&op=OP60` 返回 404（本线没这工序）
- 工位勾选"视频"后接口 reqs 变 `image,video`，取消回到 `image`；总览换型 X200→X210 成功

**终端数据层（`sync-test.cjs`，连真实服务器）**
- 内容真实落盘且 sha256 校验通过，文件数 = 清单条数，无 `.part` 残留
- 切换后旧型号独有文件被删除，磁盘只剩当前一套（A8）
- 连切三轮，文件数与占用不增长
- 断电重启后不连服务器也能在 **110ms** 内出画面（A5 的底座）
- 指向不可达地址时画面照样播、状态转离线、不抛错（A3/A4 的底座）

**终端画面（`preview.html` 七种状态逐个核对）**
- 正常播放 / 自动翻页 / 整屏切换 / 掉队红字 / 空内容不黑屏 / 准备中不遮挡 / 离线不中断

### 还没验证的

**终端窗口本身没在本机跑起来**：当前开发环境的执行会话没有桌面，Electron GUI 进程创建窗口前就退出了
（Node 模式下同样的 `main.js` 能正常执行，二进制与依赖都完好）。
所以 kiosk 全屏、托盘、看门狗 reload、开机自启这四项**需要你在自己的工作台电脑上双击验证**：
`terminal\start.bat`（生产）或 `terminal\dev.bat`（调试）。

## 九、已知限制

| 限制 | 说明 / 何时需要处理 |
|---|---|
| exe 未做代码签名 | Windows 首次运行会提示"未知发布者"，选"仍要运行"即可；规模到十几台再考虑买证书 |
| 清单改动会整批重下 | 改一张图也重下整套（约 27MB）。内容量大了再做增量 |
| 机种数量按 10 个设计 | 加机种不受限，列表按启用状态过滤 |
| 无权限、无操作日志 | 一期的明确取舍，换型记录只写进程日志 |
| 终端网卡按 WiFi 5 即可 | 27MB / 5 分钟 = 90KB/s，5 台并发 3.6Mbps，不必换 AX210 |

## 十、明确不做

- ❌ 工位**设备档案**（工位只是机种里的内容槽位，不是一台要注册的机器；屏只配 `line` + `op`）
- ❌ 分屏独立设机种（换型按线体整体切）
- ❌ 本地历史机种归档（旧内容切完即删）
- ❌ 边下边播 / 分批生效（必须备齐后整批翻）
- ❌ 视频转码（格式由工程部按规范产出：720p / H.264 / 单段 60 秒内）
- ❌ 多区域分屏、触摸交互、扫码换型
- ❌ 公网部署、加密狗
